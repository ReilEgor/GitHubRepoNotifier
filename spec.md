# Специфікація: RepoNotifier

Одна сторінка: що будуємо, з чого воно складається і за якими критеріями приймається. Формат — [standards/spec-format.md](standards/spec-format.md), деталі — в [docs/spec/](docs/spec/).

## 1. Призначення та межі

RepoNotifier стежить за релізами публічних репозиторіїв GitHub і надсилає листа підписникам, коли з'являється нова версія. Користувач вказує пошту та репозиторій, підтверджує пошту за посиланням із листа й отримує сповіщення, доки не відпишеться.

- **Входить:** підписка, підтвердження пошти, перегляд підписок, відписка; опитування GitHub; листи підтвердження й листи про реліз; REST API, gRPC API, веб-сторінка.
- **Не входить:** облікові записи з паролями; приватні репозиторії; GitHub Webhooks; канали, крім пошти; сповіщення про коміти, issues, pull requests.
- **Відкладено до Завдання 3:** брокер повідомлень, сервіс `notification`, ретранслятор outbox, споживачі черг, сканер релізів. Вони лишаються в специфікації як заплановані: у Завданні 2 вимагається лише API і база даних, а вони не мають спостережуваного результату через API. Записи в `outbox_messages` створюються вже зараз.

## 2. Компоненти

| Компонент | Відповідальність | Власні дані | Чому окремо |
|---|---|---|---|
| `subscription` | користувачі й підписки від запиту до підтвердження чи відписки | `subscription_db` | єдиний приймає запити людей; має відповідати, коли пошта недоступна |
| `tracking` | знає останній реліз кожного репозиторію й виявляє новий | `tracker_db` | єдиний звертається до GitHub; навантаження залежить від кількості репозиторіїв |
| `notification` | надсилає листи за командами з черги | немає | листи йдуть сплесками; повільна пошта не має затримувати решту |
| `shared` | контракти повідомлень, логер, `/health` і `/version` | немає | контракт існує в одному примірнику для видавця й споживача |

Рішення: [ADR-0001](docs/adr/0001-split-into-three-services.md) (три сервіси), [ADR-0003](docs/adr/0003-go-workspace-with-a-module-per-service.md) (модуль на сервіс).

## 3. Взаємодія

| Звідки | Куди | Спосіб | Контракт |
|---|---|---|---|
| користувач | `subscription` | REST | `/api/v1/subscribe`, `/subscriptions`, `/confirm/:token`, `/unsubscribe/:token` |
| `subscription` | `tracking` | gRPC | `GetOrCreateRepository` |
| `subscription` | `notification` | черга | `SendConfirmationCommand` |
| `notification` | `subscription` | черга | `ConfirmationResultEvent` |
| `subscription` | `tracking` | черга | `SubscriptionActivatedEvent`, `UnsubscriptionActivatedEvent` |
| `tracking` | `subscription` | черга | `TagUpdatedEvent` |
| `tracking` | `notification` | черга | `SendNotificationCommand` |

Єдиний синхронний зв'язок між сервісами — `subscription` → `tracking` ([ADR-0002](docs/adr/0002-publish-tag-updates-as-events.md)). Зв'язку, якого немає в цій таблиці, не має бути в коді.

## 4. Критерії прийняття

| ID | Критерій | Як перевірити |
|---|---|---|
| FR-1 | Підписка з коректними поштою та `власник/назва` приймається | `POST /api/v1/subscribe` повертає `202`; у `subscriptions` є запис із `is_confirmed = false` |
| FR-2 | Підписка на неіснуючий репозиторій або репозиторій без релізів відхиляється | немає на GitHub — `404`; немає жодного релізу — `422`; GitHub недоступний, ліміт чи тайм-аут — `503`; у всіх випадках записів не створено |
| FR-3 | Після підписки надходить лист із посиланням підтвердження | лист у поштовій скриньці; якщо надіслати неможливо — підписку видалено, сага в стані `COMPENSATED` |
| FR-4 | Підписка підтверджується за токеном | `GET /api/v1/confirm/:token` повертає `200`, `is_confirmed = true`; недійсний токен — `404`. Токен береться з бази поза кодом сервісу |
| FR-5 | Сканер перевіряє релізи кожного репозиторію, що має підписників | за один інтервал сканера кожен такий репозиторій опитано; репозиторій без підписників не опитується |
| FR-6 | Новий реліз дає лист кожному підтвердженому підписнику | після зміни тегу на GitHub лист отримують усі підтверджені й ніхто з непідтверджених |
| FR-7 | Відписатися можна посиланням із листа | `GET /api/v1/unsubscribe/:token` повертає `200`; наступний реліз листа не дає |
| FR-8 | Користувач бачить свої підписки | `GET /api/v1/subscriptions?email=` повертає `200` зі списком; для невідомої пошти — порожній список |
| NFR-1 | Повідомлення не губиться, якщо сервіс упав після фіксації зміни | зміна й запис в `outbox_messages` — в одній транзакції; після перезапуску повідомлення опубліковано |
| NFR-2 | Повторна доставка повідомлення не змінює результат | те саме повідомлення, доставлене двічі, не створює другого запису |
| NFR-3 | Повідомлення не повторюється нескінченно | після 5 невдалих публікацій запис outbox має статус `FAILED` |
| NFR-4 | Сервіс не читає й не пише в чужу базу | у кожного сервісу власний рядок підключення і власна тека міграцій |
| NFR-5 | Кожен виклик назовні обмежений у часі | недоступна залежність дає помилку за заданий час, а не зависання |
| NFR-6 | Опитування не вичерпує ліміт GitHub | повторний запит про той самий репозиторій у межах 5 хв іде в кеш |
| NFR-7 | Залежності між шарами спрямовані до `domain` | `make arch` |
| NFR-8 | Запит простежується крізь сервіси | один `request_id` у логах усіх сервісів, що обробляли запит |
| NFR-9 | Сервіс запускається й повідомляє, з якого коміту зібраний | `make smoke`: `/health` дає `200`, `/version` дорівнює `git rev-parse HEAD` |

У Завданні 2 перевіряються FR-1, FR-2, FR-4, FR-7 (відповідь і видалення підписки), FR-8, NFR-1 (атомарність запису в `outbox_messages`), NFR-4, NFR-5, NFR-6, NFR-7, NFR-8 (між `subscription` і `tracking`), NFR-9. Критерії FR-3, FR-5, FR-6, NFR-2, NFR-3 і частину NFR-1 про публікацію відкладено до Завдання 3: вони потребують брокера, `notification` і ретранслятора.
