# Вимоги до агента: Завдання 2 — сценарії на статиці, потім на БД

Цей документ — інструкція для AI-агента. Студент ставить задачі й ухвалює рішення; агент аналізує, ставить уточнювальні питання, пропонує варіанти, пише чернетки документів, код і тести. Студент переглядає, виправляє й затверджує кожен результат. Використання AI у роботі не приховується: його описано тут і в `DEFENSE.md`.

## 1. Роль агента

1. Рішення належать студентові. Агент не вигадує поведінку системи, якої немає в `spec.md` або в таблиці рішень (розділ 3), а фіксує її як питання.
2. Агент **може**: шукати прогалини й суперечності, ставити уточнювальні питання, пропонувати варіанти з компромісами, писати код, тести, міграції та конфігурацію.
3. Агент **може писати чернетки** `spec.md`, `docs/spec/*`, ADR, `docs/audit.md` і `DEFENSE.md` за рішеннями студента. Такий текст вважається чернеткою, доки студент його не переглянув; у `DEFENSE.md` вказано, що саме писав агент.
4. Якщо для кроку потрібне рішення, якого немає в розділі 3, агент **зупиняється й питає**, а не обирає сам.

## 2. Контекст

- Репозиторій: `GitHubRepoNotifier`, Go 1.25, модулі `shared`, `services/subscription`, `services/tracking`, `services/notification`, об'єднані `go.work`.
- Зараз це каркас: шари існують як пакети з `doc.go`, сервіси відповідають лише на `/health` і `/version`.
- Специфікація: `spec.md` (огляд і критерії прийняття), деталі в `docs/spec/`.
- Стандарти: `standards/` — стиль коду, git, DoD, перелік перевірок. Агент дотримується їх без винятків.
- Рішення: `docs/adr/` (ADR-0001…0008).

## 3. Рішення студента

Агент читає цю таблицю перед кожним етапом. Порожній рядок означає «не вирішено — питати».

| №   | Питання                                    | Рішення |

| 1   | Обсяг: які сервіси входять у завдання      | `subscription` (чотири сценарії через HTTP) і `tracking` (`GetOrCreateRepository` та клієнт GitHub). Брокер, `notification`, ретранслятор outbox, споживачі черг і сканер відкладено до Завдання 3: вони не мають спостережуваного результату через API. | 4   | Де межа транзакції                         | `Transactor.WithinTransaction(ctx, fn)`: сценарій оголошує межу, транзакція передається в репозиторії через контекст, `BEGIN/COMMIT` виконує реалізація в `shared/infrastructure/storage/postgres`. | 6   | Хто ініціатор запиту                       | `request_id` — ID бізнес-процесу: з заголовка `X-Request-ID` або новий UUID, повертається у відповіді. Ініціатор: пошта із запиту для `subscribe` і `subscriptions`; власник підписки за токеном для `confirm` і `unsubscribe` (для недійсного токена — `unknown`); `system` для фонових процесів. Глобальний обробник помилок логує лише `request_id`; між сервісами ініціатор не передається |
| 7   | Повторна підписка тієї самої пари          | `202` завжди. Непідтверджена пара: новий токен і новий лист підтвердження. Вже підтверджена пара: токен і підтвердження не змінюються, ні саги, ні команди в outbox немає. `Upsert` повертає `is_confirmed`, за яким сценарій це вирішує |
| 8   | Повторна відписка й гонки за токеном       | `404` на повторну відписку. `Confirm` і `Delete` повертають кількість змінених рядків; `0` → `ErrInvalidToken`, транзакція відкочується без запису події. Тест: два паралельні `unsubscribe` з одним токеном дають рівно одну `200` і одну `404` |
| 9   | Сканер релізів                             | Відкладено до Завдання 3 разом з брокером. Через API недоступний і не користувацький сценарій; у `tracking` слідів не лишає. Перед реалізацією вставка в outbox має стати пакетною |
| 10  | Збої GitHub                                | Час на спробу `GITHUB_HTTP_TIMEOUT` = 3 с. До 3 спроб (затримка 200 мс, потім 400 мс) лише для `HEAD`/`GET` і лише на тайм-аут, помилку з'єднання та `5xx`; жоден `4xx` не повторюється. Circuit breaker (`sony/gobreaker`) обгортає всю серію спроб, розмикається після 3 невдалих серій поспіль, пробні запити через 30 с, не більше 3. Коди: `404` на репозиторій — немає, `404` на останній реліз — немає релізів, `429` і `403` з `X-RateLimit-Remaining: 0` — ліміт → `503`, інший `403` та решта `4xx` → `500`; gRPC `DeadlineExceeded` → `503`. Два виклики GitHub на підписку, найгірший випадок ≈ 19,2 с; час на `POST /subscribe` — 25 с. Деталі — `docs/spec/errors.md` |

| 13  | Конфігурація                               | Змінні середовища, розбір у структуру через `caarlos0/env` |
| 14  | Redis                                      | У межах завдання: обмежувач частоти в `subscription` (10 запитів/с, `429`) і кеш GitHub у `tracking` (існування — 1 хв, реліз — 5 хв). | 16  | Статичні дані на етапі 1                   | Реальний gRPC з першого етапу: `tracking` на репозиторії в пам'яті з фіксованим списком, адаптер у `subscription` той самий, що й на БД. Перевірка заміни: `git diff --stat` етапу 2 не торкається `transport/`, `usecase/` та адаптера |
| 17  | Середовище й тести                         | Три рівні (ADR-0008): `make check` без Docker; `make test-integration` на Testcontainers за build tag `integration`; `make smoke` на Docker Compose лише в CI. Додається `make unit`. Порти Compose: `15432`, `15433`, `16379`. Контейнер на пакет тестів, `CREATE DATABASE` на тест; міграції в тестах — `golang-migrate` з коду; тест `up` → `down` → `up`. ### Крайові випадки (вирішені)

- **Репозиторій без жодного релізу.** Вирішено: підписка відхиляється новою доменною помилкою `ErrRepositoryHasNoReleases` → `422 repository has no releases`; `tracking` повертає gRPC `FailedPrecondition` і нічого не зберігає.
- **Відмова GitHub.** Ліміт — `429` або `403` із заголовком `X-RateLimit-Remaining: 0` → `503`; будь-який інший `403` — відмова в доступі, внутрішня помилка → `500`.
- **Перевірка пулу на старті** — `SELECT now()`: якщо база недоступна, сервіс не стартує.

## 4. Заборони

1. Не робити `git commit` і `git push` без явного підтвердження студента.
2. Не використовувати `--no-verify` і не послаблювати `.golangci.yml` чи `.go-arch-lint.yml` без окремого дозволу.
3. Не писати SQL поза `repository/`. Транзакцію відкриває лише реалізація `Transactor` у `shared/infrastructure/storage/postgres`; сценарій оголошує межу через інтерфейс `Transactor` і не імпортує драйвер бази (ADR-0007).
4. Не ставити HTTP-коди відповіді в обробниках через `switch` — лише в глобальному обробнику помилок.
5. Не передавати `request_id` чи ініціатора параметрами функцій і не додавати їх у лог вручну.
6. Не створювати штучних проблем (наприклад, N+1) заради пункту в аудиті.
7. Не змінювати вже затверджені `spec.md`, `docs/spec/*` та ADR без прохання студента; зміна змісту рішення — лише після його підтвердження.
8. Не використовувати стандартні порти PostgreSQL на localhost (5432, 5433, 5434).

## 5. Етапи

Кожен етап закінчується зеленим `make check` і звітом (розділ 7). Наступний етап починається лише після підтвердження студента.

### Етап 0. Аналіз специфікації

1. Прочитати `spec.md`, `docs/spec/*`, `docs/adr/*`.
2. Скласти список прогалин для чотирьох сценаріїв (підписка, підтвердження, перегляд, відписка):
   - поведінка, яку не описано;
   - суперечності між документами;
   - гілки збою без результату;
   - HTTP-коди, яких немає в каталозі помилок.
3. Скласти чернетку двох довідкових таблиць як **факти й варіанти**, без остаточних формулювань:
   - перелік SQL-запитів: метод репозиторію → запит → транзакція;
   - каталог помилок: доменна помилка → HTTP-код.
4. Віддати студенту питання. Нічого не комітити.

**Готово, коли:** студент відповів на питання й затвердив оновлений spec.

### Етап 1. Прототип на статичних даних

1. `domain/usecase`: інтерфейс сценаріїв `Subscribe`, `Confirm`, `List`, `Unsubscribe`.
2. `domain/repository`: інтерфейси репозиторіїв «одна таблиця — один репозиторій» плюс `Transactor` з одним методом (рішення 4).
3. `usecase`: реалізація бізнес-правил за `docs/spec/scenarios.md`.
4. `repository/memory`: реалізація в пам'яті з `sync.Mutex`.
5. `tracking`: реальний gRPC-сервер `GetOrCreateRepository` на репозиторії в пам'яті з фіксованим списком (рішення 16); клієнт у `subscription/infrastructure/adapter`; `api/proto/v1` і кодогенерація.
6. `transport/http`: чотири шляхи — `POST /api/v1/subscribe`, `GET /api/v1/confirm/{token}`, `GET /api/v1/subscriptions?email=`, `GET /api/v1/unsubscribe/{token}`.
7. Глобальний обробник помилок і перехоплення `panic`.
8. Проміжний обробник контексту: `request_id` (з `X-Request-ID` або новий) та ініціатор у `context.Context`.
9. Власний `slog.Handler`, що додає `request_id` та ініціатора до кожного запису з контексту.
10. Збирання залежностей у `cmd` через `wire` (рішення 5).
11. Тести сценаріїв на репозиторіях у пам'яті: успіх, кожна доменна помилка, атомарність (знімок і відкат), «`txCtx` справді використано».
12. Тест глобального обробника: кожна доменна помилка дає свій код.

**Готово, коли:** усі чотири сценарії проходять через `curl` без бази; у логах кожного запиту є `request_id`; `make check` зелений.

**Коміти:** окремо — контекст і логування; глобальний обробник; сценарії та репозиторії в пам'яті; HTTP-шляхи.

### Етап 2. Інтеграція БД

1. `docker-compose.yml` з PostgreSQL для `subscription_db` і `tracker_db` та Redis на портах `15432`, `15433`, `16379`; `.env.example` і таблиця змінних у `README.md`.
2. Міграції за `docs/spec/data.md` для обох сервісів, кожна `up` з `down`.
3. Ініціалізація пулу на старті з `SELECT now()`; якщо база недоступна — сервіс завершується з помилкою одразу.
4. `repository/postgres`: ті самі інтерфейси, SQL — іменовані константи, параметри лише позиційні.
5. Транзакції за таблицями змін даних у `docs/spec/scenarios.md`: підписка — `users`, `subscriptions`, `subscription_sagas`, `outbox_messages` в одній транзакції.
6. Ідемпотентність і гонки за рішеннями 7 і 8: `Upsert` не змінює вже підтверджену пару; `Confirm` і `Delete` повертають кількість рядків.
7. `tracking`: клієнт GitHub з часом очікування й повторами (рішення 10); `404` → «не існує», `429` і `5xx` → «недоступний».
8. Заміна реалізацій у `cmd`: пам'ять → PostgreSQL. **Файли в `transport/` і `usecase/` у цьому етапі не змінюються.** Якщо змінити довелося — зупинитися й пояснити студенту причину.
9. Інтеграційні тести на Testcontainers за build tag `integration`: контейнер на пакет, `CREATE DATABASE` на тест, сід із `migrations/testdata/` (рішення 15, 17).
10. Тест кількості запитів через трасувальник `pgx`: перегляд підписок — один запит незалежно від кількості підписок.
11. Тести збоїв GitHub на фейковому HTTP-сервері: `429`, `500`, затримка.
12. `make smoke` на Docker Compose (лише CI): підписка → підтвердження (токен із бази) → перегляд → відписка. Тест `up` → `down` → `up` для міграцій. Цілі `unit`, `integration` у `scripts/check.sh`; `pre-push` запускає `unit` і збірку.

**Готово, коли:** сценарії працюють через той самий API на БД; diff етапу не зачіпає `transport/` і `usecase/`; `make check` і інтеграційні тести зелені.

**Коміти:** окремо — середовище й міграції; пул; репозиторії `subscription`; репозиторії й клієнт GitHub у `tracking`; заміна в `cmd`; тести.

### Етап 3. Матеріали для аудиту

1. Зібрати факти, кожен із SHA коміту:
   - зрізані кути й крайові випадки, які лишилися;
   - де міг виникнути або виник N+1 і як закрито;
   - поведінка на збоях: база недоступна на старті й посеред роботи, GitHub недоступний, повільний, обмеження запитів.
2. Перевірити, що `README.md`, `standards/checks.md` і `Makefile` відповідають новим командам.

**Готово, коли:** студент переглянув і затвердив аудит, ADR і `DEFENSE.md`; у `DEFENSE.md` вказано, де використано AI.

## 6. Перевірки на кожному кроці

- `make check` після кожного логічного кроку, не лише наприкінці етапу.
- Новий пакет або нова залежність між шарами — спершу питання студенту, потім правка `.go-arch-lint.yml`.
- Кожна нова змінна середовища — у `README.md`.
- Тести — табличні, назви випадків `success - …` / `error - …`.

## 7. Звіт після етапу

1. Що зроблено — по пунктах етапу.
2. Що не зроблено й чому.
3. Результат `make check` та інших тестів — вивід, а не переказ.
4. Рішення, які агент прийняв сам, якщо такі були, з обґрунтуванням.
5. Питання до студента перед наступним етапом.
6. Запропоновані повідомлення комітів.
