## Початок промпту

Ти реалізуєш Завдання 2 курсу: основні сценарії RepoNotifier спершу на статичних даних через HTTP API, потім на справжній базі PostgreSQL. Це проєкт на Go в репозиторії, де вже є специфікація, ADR і стандарти. **Спершу ти складаєш план реалізації й чекаєш мого слова «можеш починати». Без нього ти не пишеш жодного рядка коду.**

### 1. Твоя роль

Ти пишеш **код, тести, міграції, конфігурацію й скрипти**. Рішення ухвалюю я. Специфікацію, ADR, аудит і `DEFENSE.md` пишу я.

- Якщо під час роботи виявляєш, що документ суперечить коду чи іншому документу, **не змінюй документ**: опиши проблему в чат і запропонуй формулювання.
- Єдині документи, які ти оновлюєш, — ті, що просто описують код, який ти створив: таблицю змінних середовища й команди в `README.md` та `standards/checks.md`. Усе інше — тільки пропозиція.
- Не вигадуй поведінки, якої немає в документах. Якщо рішення бракує — зупинись і запитай.

### 3а. Гілка й git

Уся робота йде на окремій гілці **`feat/subscription-api-and-postgres`**, створеній від `main`.

**Перед першим рядком коду перевір:**

1. `git branch --show-current` — ти на `feat/subscription-api-and-postgres`. Якщо гілки ще немає, створи її локально від `main`: `git switch -c feat/subscription-api-and-postgres main`. На `main` не коміть ніколи.
2. Гілка містить актуальні документи Завдання 2: існують `docs/spec/api.md`, `docs/spec/queries.md`, `docs/spec/errors.md` і `docs/adr/0008-environment-and-integration-tests.md`. Якщо їх немає, **зупинись і скажи мені**: документи ще не злито в `main`, і гілку треба будувати після їхнього злиття.
3. `git status` чистий (немає чужих незакомічених змін).

**Що тобі дозволено:**

- `git add` і `git commit` на цій гілці, коли логічний крок завершено, `make check` зелений і ти показав мені, що саме комітиш. Окремий дозвіл на кожен коміт не потрібен.
- Повідомлення комітів — Conventional Commits, англійською, за `standards/git-workflow.md`: один коміт — одна змістовна зміна. Не склеюй в один коміт різні кроки етапу.
- Читати історію й порівнювати: `git log`, `git diff`, `git status`, `git show`.

**Що тобі заборонено:**

- `git push` у будь-якому вигляді, `git merge`, `git rebase`, `git reset --hard`, `git push --force`, перемикання на інші гілки з незакоміченими змінами, видалення гілок і тегів, створення PR. **Push і merge виконую я.**
- `--no-verify`. Якщо hook відхилив коміт, виправ причину. Не обходь і не вимикай hook.
- Коміти, що не проходять `make check`: кожен коміт на гілці має збиратися й проходити перевірки.

Після кожного етапу у звіті вкажи список комітів гілки (`git log --oneline main..HEAD`), щоб я бачив, що піде в PR.

### 4. Рішення, на яких ти будуєш

Це підсумок; джерело правди — документи з розділу 2.

| Тема | Рішення |
|---|---|
| Виклик `subscription` → `tracking` | gRPC з першого етапу; ключ API й `request_id` у метаданих |
| Статика | `tracking` на репозиторії в пам'яті з фіксованим списком; негативні гілки через імена `static/…` |
| БД | `pgx/v5`, пул `pgxpool`, сирий SQL константами, позиційні параметри, без ORM |
| Транзакції | `Transactor.WithinTransaction(ctx, fn)`; `BEGIN/COMMIT` лише в реалізації в `shared/infrastructure/storage/postgres`; у пам'яті — знімок і відкат під м'ютексом |
| Залежності | `google/wire` з першого етапу; ресурси через конструктори |
| Контекст | `request_id` та ініціатор у `context.Context`; власний `slog.Handler` додає їх у кожен запис; глобальний обробник логує лише `request_id` |
| Помилки | один глобальний обробник (Gin), доменні помилки через `errors.Is`, `panic` перехоплює окремий проміжний обробник |
| Повторна підписка | завжди `202`; підтверджена пара не змінюється й не створює ні саги, ні команди в outbox |
| Гонки | `Confirm` і `Delete` повертають кількість рядків; `0` → `ErrInvalidToken`, відкат, події немає |
| GitHub | 3 спроби, 200 і 400 мс, лише `HEAD`/`GET` на тайм-аут, помилку з'єднання, `5xx`; circuit breaker обгортає серію; ліміт → `503`; `DeadlineExceeded` → `503` |
| Час на `POST /subscribe` | 25 с; на решту 3 с |
| Redis | обмежувач частоти (fail-open) і кеш GitHub |
| Токени | беруться з бази поза кодом сервісу; сід тестів у `migrations/testdata/` |
| Тести | перевага інтеграційним (Testcontainers, build tag `integration`); модульні лише для того, що через БД не перевірити |

### 5. Етапи

Кожен етап закінчується зеленим `make check` і звітом (розділ 8). Наступний етап ти починаєш лише після мого підтвердження.

#### Етап 1. Прототип на статичних даних

1. Контекст і логування: `WithInitiator`/`Initiator` у `shared/ctxlog`, власний `slog.Handler`, проміжний обробник `X-Request-ID`.
2. Глобальний обробник помилок і перехоплення `panic`; каталог з `errors.md`.
3. Інтерфейси: `domain/usecase` (`Subscribe`, `Confirm`, `List`, `Unsubscribe`), `domain/repository` («одна таблиця — один репозиторій» і `Transactor`).
4. `repository/memory` у `subscription` і `tracking`; знімок і відкат у реалізації `Transactor`.
5. Сценарії за `scenarios.md`.
6. gRPC: `api/proto/v1`, `buf`-конфігурація, сервер у `tracking`, клієнт у `subscription/infrastructure/adapter`.
7. HTTP-шляхи за `api.md`, перевірка вхідних даних у транспорті.
8. Збирання залежностей через `wire` у `cmd`.
9. Обмежувач частоти й кеш — на `miniredis` у тестах.
10. Тести: кожна доменна помилка, атомарність (знімок і відкат), «`txCtx` справді використано», глобальний обробник, `slog.Handler`, `X-Request-ID`.

**Готово, коли:** чотири шляхи працюють через `curl` без бази; негативні гілки `tracking` дають `404`, `422`, `503`; кожен запис логу має `request_id`; `make check` зелений.

**Коміти:** контекст і логування; глобальний обробник; сценарії й пам'ять; gRPC; HTTP; `wire`.

#### Етап 2. Інтеграція БД

1. `docker-compose.yml` (PostgreSQL ×2, Redis) на портах `15432`, `15433`, `16379`; `.env.example`; таблиця змінних у `README.md`.
2. Міграції за `data.md`; кожна `up` має `down`; сід тестів — у `migrations/testdata/`.
3. Пул на старті з `SELECT now()`: недоступна база — сервіс не стартує.
4. `repository/postgres` на тих самих інтерфейсах; SQL за `queries.md`; `Transactor` у `shared/infrastructure/storage/postgres`.
5. `tracking`: клієнт GitHub із часом на спробу, повторами й circuit breaker; кеш у Redis.
6. Заміна реалізацій у `wire`.
7. Інтеграційні тести: контейнер на пакет, `CREATE DATABASE` на тест, `golang-migrate` з коду, тест `up` → `down` → `up`.
8. Тест кількості запитів через трасувальник `pgx`: перегляд підписок — один запит.
9. Тест гонок: два паралельні `unsubscribe` з одним токеном — рівно одна `200` і одна `404`.
10. Тести збоїв GitHub на фейковому HTTP-сервері: `429`, `403` з `X-RateLimit-Remaining: 0`, інший `403`, `500`, повільна відповідь.
11. Цілі `unit`, `integration`, `smoke` у `scripts/check.sh` і `Makefile`; `pre-push` запускає `unit` і збірку; `smoke` на Compose для CI.

**Правило етапу:** файли в `transport/`, `usecase/` і `infrastructure/adapter/` **не змінюються**. Перевір командою `git diff --stat` по цих теках. Якщо змінити довелося, **зупинись і поясни причину**: це означає, що межі шарів зроблено неправильно.

**Готово, коли:** ті самі чотири шляхи працюють на БД; `make check` і інтеграційні тести зелені; diff етапу не зачіпає перелічених тек.

**Коміти:** середовище й міграції; пул; репозиторії `subscription`; репозиторії та клієнт GitHub у `tracking`; заміна в `wire`; тести; скрипти.

#### Етап 3. Факти для аудиту

Не пиши аудит: збери факти, кожен із SHA коміту. Три групи:

- зрізані кути й крайові випадки, які лишилися;
- де виникав або міг виникнути N+1 і як закрито;
- поведінка на збоях: база недоступна на старті й посеред запиту, GitHub недоступний, повільний, ліміт, Redis недоступний.

### 6. На що звернути особливу увагу

Це місця, де помилки найімовірніші. Перевіряй їх свідомо.

**Межі шарів**

- У `usecase/` немає SQL, `pgx`, Gin, gRPC, Redis. `go-arch-lint` не пустить, але не вважай це гарантією: обхід через інтерфейс, оголошений у транспорті, він не бачить.
- Обробник HTTP не ставить код відповіді через `switch`: він повертає помилку, а код ставить глобальний обробник.
- `fmt.Sprintf` у `internal/repository` заборонено лінтером. SQL — константа з `$n`.
- Усередині транзакції немає викликів назовні (`tracking`, GitHub, Redis).

**Транзакції та контекст**

- Усередині `WithinTransaction` репозиторіям передається `txCtx`, а не зовнішній `ctx`. Помилка тут не видна без тесту.
- `Subscribe` спершу викликає `tracking`, потім відкриває транзакцію (`користувач`, `підписка`, `сага`, `outbox`); не навпаки.
- `Upsert` повертає `is_confirmed`; саме за ним сценарій вирішує, чи створювати сагу й команду.
- `request_id` не передається параметрами й не додається в лог вручну.

**Помилки й гонки**

- Кожне `UPDATE`/`DELETE` за токеном перевіряє кількість рядків.
- Репозиторій перекладає «рядок не знайдено» на доменну помилку; вище про `pgx` ніхто не знає.
- Помилку логує тільки глобальний обробник, один раз.

**Безпека**

- Токен не повертається API і не потрапляє в логи.
- Ключ API й токени в тестах — вигадані; в репозиторій не потрапляють `.env` та реальні секрети.

**GitHub**

- Тести не звертаються до справжнього GitHub.
- Тайм-аут спроби 3 с, повторів не більше 2; час на всю операцію вкладається в 25 с.
- Circuit breaker рахує серію спроб як один збій.

**Середовище (Windows)**

- Команди `make` виконуй із Git Bash через `mingw32-make`; у PowerShell скрипти не працюють, бо немає `sh`.
- Для Testcontainers потрібен запущений Docker Desktop. Перевір це на початку, а не після написання тестів.
- Не використовуй порти 5432–5434 і 6379.

### 7. Правила роботи

1. **Спершу план.** Після читання склади план за форматом нижче й чекай «можеш починати».
2. **Git — за розділом 3а:** коміти на `feat/subscription-api-and-postgres` дозволені, `push`, `merge`, `rebase` і `reset --hard` заборонені.
3. **`make check` після кожного логічного кроку**, не лише наприкінці етапу.
4. **Нова залежність між шарами, нова стороння бібліотека чи зміна `.go-arch-lint.yml` / `.golangci.yml` — спершу питання мені.** Перелічи нові бібліотеки в плані: `gin`, `pgx`, `go-redis`, `miniredis`, `wire`, `grpc`, `protobuf`, `gobreaker`, `golang-migrate`, `testcontainers-go`. Для кожної скажи, у якому модулі й навіщо.
5. **Не вимикай й не послаблюй** лінтер, перевірки меж шарів і тести. `--no-verify` заборонено.
6. Одна змінна середовища — один рядок у таблиці `README.md` у тому самому коміті.
7. Тести табличні, назви випадків `success - …` / `error - …`.
8. Згенерований код (`wire_gen.go`, protobuf) не редагуй вручну. Запропонуй у плані, як перевіряти його актуальність у CI.
9. Не виходь за обсяг. Усе, що стосується брокера й сканера, — Завдання 3.

### 8. Коли зупинитися й запитати

- Рішення немає в документах, а воно потрібне для наступного кроку.
- Документ суперечить коду або іншому документу.
- Для кроку треба змінити `transport/`, `usecase/` або адаптер на етапі 2.
- Потрібна нова залежність, правило лінтера чи межі шарів.
- Той самий тест не вдається виправити після двох спроб: опиши, що пробував, і не обходь його.
- Docker чи інше середовище не працює.

### 9. Формат плану (перший крок)

Після читання дай план. Кожен етап:

- **Що робимо** — одне-два речення.
- **Файли й пакети** — що створюється чи змінюється, у яких шарах.
- **Джерело** — документ і розділ, за яким це робиться.
- **Критерій завершення** — команда, відповідь API чи стан даних.
- **Залежить від** — які кроки мають бути раніше.
- **Ризики**.
- **Коміти** — як розбити.

Окремо додай:

- план тестів: що перевіряє модульний, що інтеграційний, як перевіряється відсутність N+1;
- список нових бібліотек із обґрунтуванням;
- де лежатиме згенерований код `protobuf` і як CI перевірятиме його актуальність;
- питання до мене, якщо є.

Закінчи словами «Чекаю на ваше погодження плану».

### 10. Формат звіту після кожного етапу

1. Що зроблено — по пунктах етапу.
2. Що не зроблено й чому.
3. Вивід `make check`, інтеграційних тестів і `git diff --stat` для перевірки меж — **вивід, а не переказ**.
4. Рішення, які ти ухвалив сам, із обґрунтуванням. Їх має бути мінімум.
5. Знайдені розбіжності в документах: що саме й що пропонуєш.
6. Факти для аудиту, що з'явилися на цьому етапі.
7. Коміти гілки з їхніми SHA (`git log --oneline main..HEAD`).
8. Питання до мене перед наступним етапом.

### 11. Мова й стиль

Відповідай українською. Пояснюй, чому, а не лише що. Посилайся на файл і рядок. Код, ідентифікатори й коментарі в коді — англійською, як у `standards/README.md`.

Почни з читання документів. Коли прочитаєш, напиши, що саме прочитав і чи є розбіжності, а потім дай план.

## Примітки до промпту (не копіювати)

- Розділ 6 свідомо перелічує слабкі місця. Якщо хочете перевірити, чи агент знаходить їх сам, видаліть його, але вимоги розділів 1, 7 і 8 лишіть.

Якщо вони лишилися незакоміченими, гілка не міститиме специфікації, і агент зупиниться на перевірці в розділі 3а.
