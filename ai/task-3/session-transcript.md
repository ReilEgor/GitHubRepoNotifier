## 1. Користувач: постановка завдання

> Мета: unit + інтеграційні + E2E + мутаційне тестування.
>
> Що зробити:
> • Передумова: розумне покриття критичної логіки (гілки, не лише рядки).
> • Unit-тести (повне покриття ≥1 модуля), інтеграційні (з підняттям залежностей: БД, HTTP-сервер), E2E.
> • Мутаційне тестування (Stryker / PIT / mutmut / cosmic-ray). Звіт: класифікувати вижилих мутантів (реальна прогалина / еквівалентний / прийнятний).
> • Аудит: топ-3, де «зелені» тести не ловлять реальні баги; підсилити.
> • DEFENSE.md: аналіз ефективності тестів + make mutation для відтворення.
>
> Ознаки відмінного виконання: є всі рівні тестів; звіт мутацій із класифікацією вижилих; видно підсилення слабких тестів; прогін відтворюваний.
>
> як будем це робити опиши план

### Дії асистента
Переглянув структуру репозиторію (`git ls-files`, Makefile, `scripts/check.sh`, ADR-0008, harness інтеграційних тестів) і виміряв поточне покриття `go test -cover`.

### Відповідь асистента (план)

**Що вже було:** unit — `usecase` 87–89%, `http` 95.8%, `middleware` 87.7%, `github client` 83.9%, `grpc` 67.3%; інтеграційні тести з Testcontainers у `subscription`; E2E лише як shell-`smoke` без асертів; мутацій немає. Покриття рахувалося по рядках, для «гілок» потрібен окремий підхід.

**Етапи:**
1. Базова лінія: `make cover`, таблиця «модуль → %» для критичної логіки.
2. Unit: повне покриття одного модуля (пропозиція — `ratelimit`), гілки помилок у `usecase`, табличні тести з `-race`.
3. Інтеграційні: розширити Testcontainers-тести (outbox, saga, `tracking` repository, негативні сценарії HTTP).
4. E2E: справжній тест на Go під тегом `e2e` замість shell-smoke, із мокованим GitHub.
5. Мутації: `gremlins` (запасні — `go-mutesting`, `ooze`), цикл по модулях через `go.work`, звіт у `reports/mutation/`, класифікація вцілілих.
6. Аудит топ-3 «зелених, але сліпих» тестів (кандидати: `ratelimit`, `middleware/errors`, компенсація saga).
7. `DEFENSE.md`: піраміда тестів, покриття до/після, mutation score, відтворення.
8. Відтворюваність і CI: усе через `scripts/check.sh`, версії зафіксовано, ADR-0009.

Порядок: базова лінія → мутації на unit → підсилення топ-3 → інтеграційні → E2E → `DEFENSE.md` і CI. Питання: який модуль брати для повного покриття, чи підходить `gremlins`, чи запущений Docker Desktop.

## 2. Користувач: уточнення й дозволи

> Потрібно покрити тестами критичну логіку.
> Використаємо декілька видів тестув: мутацыйні(гремлінс), інтеграційними треба покрити основні флоу. Основний упор варто робити до інтеграційних тестів, замість юнітів. Вважаю, що краще тестувати поведінку, а не код. Пропоную додати скрипт який буде виводити відсоток покриття, так буде краще під час написання тетсів. Для повного покриття модуля пропоную обрати ratelimit. Для E2E тестів пропоную використати плейварйт. Так само для зручності створи мейк файлів для перевикористання. Адудит зроблю пізніше, окремо. Для початку варто розписати основний код, пілся цього я проведу ревью змін, допрацюю прогалини. Гілку я створив, коміти досволяю робити і пушити. Під кінець роботи свори мд файл з описом змін. Якщо є питання задай мені їх в цій сессії, також зафіксуй їх у вихідному мд, буду робити аудит.

### Дії асистента (хронологічно)

1. **Розвідка:** гілка `feat/tests-realization`, стандарти тестів (`standards/code-style.md` §14), `ratelimit`, `check.sh`, CI, чи встановлений `gremlins` (так, v0.6.0).
2. **`ratelimit`:** gremlins на старих тестах показав: гілка `H` не покрита, `redisTimeout` не покритий. Додано тести (година, від'ємні й порожні значення, межа ліміту, вікно не подовжується, завислий Redis, відсутність повторів).
3. **Знайдено помилку:** тест «Redis мовчить» показав 3 с замість 0.2 с. Причина: клієнт без `ContextTimeoutEnabled`. Виправлено через `ratelimit.NewClient` і ту саму опцію в кеші `tracking`.
4. **Скрипти:** `cover`, `cover-unit`, `mutation`, `e2e` у `check.sh` і Makefile; блок запуску системи зі `smoke` винесено в `stack_up`/`stack_down`. По дорозі виправлено: дедуплікацію блоків профілю, `go list -m` у workspace, сортування через `sort.exe` Windows (замінено сортуванням в awk).
5. **Інтеграційні:** `redistest` (контейнер Redis), `journey_test.go` у `subscription`, новий пакет `tracking/internal/integration`. Перший запуск завис через Ryuk на Windows (`TESTCONTAINERS_RYUK_DISABLED=true`). Лінтер: `errcheck`, `gci`, `golines`, `wrapcheck`, `govet shadow`: виправлено.
6. **E2E:** проєкт Playwright (режим API, бо веб-сторінки немає), фейковий GitHub на Node, 23 тести. Перший прогін: 22 з 23; падіння було помилкою тесту (7 запитів з однієї адреси при ліміті 5), виправлено.
7. **Мутації:** gremlins падає на `./pkg/...`, тому цілі розбито; типові мутатори вузькі, додано `invert-logical`, `invert-loopctrl`, `invert-assignments`. Результат: 0 вцілілих на всіх таргетах.
8. **CI:** job `e2e`, `coverage`, `mutation`. **Перевірка:** `fmt-check`, `lint`, `arch`, `unit`, `build` проходять.
9. **Документи:** ADR-0009 і `docs/testing-changes.md`.
10. **Коміти й push:** сім логічних комітів за Conventional Commits.

### Відповідь асистента (підсумок)

Гілку `feat/tests-realization` запушено, в ній сім комітів. Локально проходять `fmt-check`, `lint`, `arch`, `unit` з `-race` і `build`. Інтеграційні тести, `make e2e` (23/23) і `make smoke` теж проходять локально. Нові CI-завдання ще не запускались.

**Що зроблено:**
- Unit, `ratelimit`: покриття 100%, вцілілих мутантів нуль.
- Інтеграційні: основні флоу на реальних PostgreSQL і Redis. У `subscription`: шлях підписника, автентифікація, rate limit. У `tracking`: gRPC → use case → PostgreSQL → GitHub-клієнт проти фейкового GitHub, з Redis-кешем.
- E2E, Playwright: 23 тести проти всієї системи.
- Покриття: `make cover` і `make cover-unit`, поріг через `COVER_MIN`.
- Мутації: `make mutation` на 7 критичних пакетах, JSON-звіти.
- CI: `e2e`, `coverage`, `mutation`. ADR-0009 і `docs/testing-changes.md`.

**Результати покриття:**

| Модуль | До | Після |
|---|---|---|
| subscription | 81.1% | 93.8% |
| tracking | 78.0% | 86.6% |
| shared | 27.1% | 68.2% |

Покриття гілок Go не вимірює, лише оператори. Гілки перевіряють мутатори умов. **Вцілілих мутантів немає**, але це слабкий сигнал: gremlins не видаляє виклики й не підміняє значення, що повертаються, а інтеграційні тести в мутаціях не беруть участі.

**Знайдена помилка:** тайм-аут Redis у rate limiter не працював (клієнт без `ContextTimeoutEnabled`, go-redis ігнорував дедлайн контексту, завислий Redis тримав кожен запит ~3 с). Виправлення змінює продакшен-код.

**Питання до користувача:**
1. Loopback у unit-тесті `ratelimit`: лишити чи перенести під `integration`?
2. Спробувати `go-mutesting` перед аудитом, щоб знайти вцілілих?
3. Дублювання unit-тестів `http`/`usecase` та інтеграційних: видаляти чи лишити як швидкий шар?
4. Поріг `COVER_MIN` і `MUTATION_MIN_EFFICACY` у CI?
5. Чи потрібен Node.js, якщо веб-сторінки не буде?

**Обмеження:** покриття `usecase` на початку 89.9%, зараз 87.0%, причину не знайшов; gremlins хибно позначає як «not covered» два `case` у `handler.go`; на Windows gremlins потребує одного воркера й довгого таймауту; ADR-0009 додано без запиту. Каталоги `Code/Standards/` і `Code/Tests/` в AI second brain порожні.

Setup suggestion: додати в `local.md` рядок про `TESTCONTAINERS_RYUK_DISABLED=true` для Windows.
