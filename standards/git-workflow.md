# Робота з Git

## Гілки

- `main` завжди зелена: з неї можна зібрати й запустити систему.
- Прямі коміти в `main` заборонені. Зміна потрапляє туди лише через pull request.
- Гілка називається `<тип>/<короткий-опис>` малими літерами через дефіс:

  ```
  feat/subscription-saga
  fix/outbox-poison-messages
  docs/spec-data-model
  chore/git-hooks
  ```

- Одна гілка — одна задача. Гілка живе не довше кількох днів.

## Коміти

Формат — Conventional Commits.

```
<тип>(<область>): <що зроблено>
```

| Тип | Коли |
|---|---|
| `feat` | нова поведінка для користувача або іншого сервісу |
| `fix` | виправлення помилки |
| `refactor` | зміна структури без зміни поведінки |
| `test` | лише тести |
| `docs` | лише документація |
| `chore` | інструменти, залежності, конфігурація |
| `ci` | конвеєр CI та hooks |

Інших типів немає. Скорочення на кшталт `ref` не приймаються.

Область необов'язкова; якщо є, це назва модуля: `subscription`, `tracking`, `notification`, `shared`, `deployments`.

Правила для опису:

- англійською, у наказовому способі, з малої літери, без крапки: `add publisher confirms to outbox relay`;
- до 72 символів;
- описує, що змінилося в поведінці, а не який файл редагували.

Приклади:

```
feat(tracking): cache GitHub release responses in Redis
fix(notification): requeue confirmation command if saga result publish fails
refactor: split services into independent modules
```

### Чого не має бути в історії

- **Комітів `fix: linter`.** У попередній версії їх щонайменше вісім серед останніх шістдесяти комітів: лінтер запускався лише в CI, тож помилка стилю коштувала окремого коміту й очікування конвеєра. Тепер hook не пропускає такий код, і виправлення потрапляє в той самий коміт, що й зміна.
- **Комітів, які не збираються.** Кожен коміт у `main` проходить `make check`.
- **Змішаних комітів.** Рефакторинг і нова поведінка — два різні коміти: рефакторинг має проходити старі тести без змін.

## Pull request

1. Гілка оновлена відносно `main`.
2. Локально пройдено `make check`.
3. Опис відповідає на три питання: що змінено, навіщо, як перевірити.
4. Якщо змінюється архітектура, межі модулів або додається залежність, у тому самому pull request є ADR та оновлений `spec.md`.
5. CI зелений.
6. Виконано [Definition of Done](definition-of-done.md).

Pull request зливається зі збереженням комітів, якщо кожен із них осмислений і проходить перевірки; інакше — одним комітом (squash).

## Заборонено

- `git commit --no-verify` та `git push --no-verify`. CI повторює ті самі перевірки, тож обхід hook лише відкладає відмову.
- `git push --force` у `main`.
- Коміт файлів `.env`, ключів і токенів. Якщо секрет потрапив у репозиторій, його замінюють на новий; видалення з історії його не рятує.
