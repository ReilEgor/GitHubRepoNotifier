# Стиль коду

Правила написання коду в усіх модулях: `services/subscription`, `services/tracking`, `services/notification`, `shared`.

Позначка **[авто]** означає, що правило перевіряє інструмент і порушення блокує коміт. Решту перевіряє рецензент.

## 1. Формат

| Правило | Значення | Інструмент |
|---|---|---|
| Форматування | `gofumpt` з додатковими правилами | **[авто]** |
| Довжина рядка | до 120 символів | **[авто]** `golines` |
| Порядок імпортів | стандартна бібліотека → сторонні → порожні → псевдоніми → власний модуль, групи розділені порожнім рядком | **[авто]** `gci` |
| Коментарі | закінчуються крапкою | **[авто]** `godot` |
| `TODO`, `FIXME`, `BUG`, `HACK` | заборонені в коді | **[авто]** `godox` |

Незавершену роботу фіксує issue, а не коментар: коментар `TODO` ніхто не відстежує.

## 2. Межі складності

| Метрика | Поріг | Лінтер |
|---|---|---|
| Довжина функції | 120 рядків або 50 інструкцій | **[авто]** `funlen` |
| Цикломатична складність | 15 | **[авто]** `gocyclo` |
| Когнітивна складність | 20 | **[авто]** `gocognit` |
| Глибина вкладених `if` | 5 | **[авто]** `nestif` |

У файлах `_test.go` `funlen`, `gocognit` і `nestif` вимкнені: табличний тест із багатьма випадками довгий за природою. Пороги не піднімаються заради однієї функції — функція ділиться.

## 3. Шари та залежності

Кожен сервіс має однакові шари. Залежності спрямовані лише всередину, до `domain`. **[авто]** `go-arch-lint`.

| Шар | Тека | Що містить | Може залежати від | Сторонні бібліотеки |
|---|---|---|---|---|
| Модель | `internal/domain/model` | сутності, доменні помилки | — | ні |
| Інтерфейси репозиторіїв | `internal/domain/repository` | контракти доступу до даних | модель | ні |
| Інтерфейси сценаріїв | `internal/domain/usecase` | контракти бізнес-операцій | модель | ні |
| Сценарії | `internal/usecase` | бізнес-логіка | модель, інтерфейси | лише `uuid` |
| Репозиторії | `internal/repository/postgres` | SQL | модель, інтерфейси репозиторіїв | так |
| Інфраструктура | `internal/infrastructure` | брокер, зовнішні клієнти, outbox | модель, інтерфейси | так |
| Транспорт | `internal/transport` | HTTP, gRPC, споживачі черги | модель, інтерфейси сценаріїв | так |
| Точка входу | `cmd` | збирання залежностей, запуск | усе | так |

Наслідки, які треба тримати в голові:

- сценарій не знає про Gin, pgx, AMQP чи gRPC — він отримує інтерфейси;
- транспорт не звертається до репозиторію напряму, лише через сценарій;
- сервіс не імпортує `internal` іншого сервісу. Спільне лежить у `shared`, а спілкування йде через gRPC або чергу;
- з `shared` у будь-який шар можна брати лише `ctxlog` і `contracts`. Решта `shared`, зокрема метрики, доступна тільки репозиторіям, інфраструктурі, транспорту та `cmd`: сценарій не вимірює сам себе, його обгортають.

Новий шар або нова дозволена залежність — це зміна `spec.md` і `.go-arch-lint.yml` в одному pull request.

## 4. Іменування

| Що | Правило | Приклад |
|---|---|---|
| Пакет | одне слово малими літерами | `usecase`, `postgres`, `rabbitmq` |
| Файл | `<сутність>_<роль>.go` | `subscription_repository.go`, `user_usecase.go` |
| Конструктор | `New<Тип>` | `NewSubscriptionRepository` |
| Інтерфейс | іменник за роллю, без префікса `I` | `SubscriptionRepository`, `EmailSender` |
| Абревіатури | великими літерами **[авто]** | `userID`, `baseURL`, `HTTPPort` |
| Доменна помилка | `Err<Що сталося>` **[авто]** | `ErrRepositoryNotFound` |
| Константа запиту | `<дія><Сутність>Query` | `deleteSubscriptionByIDQuery` |
| Псевдонім імпорту `shared` | `shared<Пакет>` | `sharedPostgres`, `sharedRabbitmq` |

## 5. Інтерфейси

- Інтерфейс, яким користуються кілька шарів, оголошується в `internal/domain`.
- Широкий інтерфейс репозиторію складається з вузьких: `SubscriptionReader` + `SubscriptionWriter` = `SubscriptionRepository`. Споживач приймає найвужчий, якого йому досить.
- Інтерфейс, потрібний одному споживачу, оголошується поруч зі споживачем, а не в `domain`.
- Над кожним інтерфейсом, для якого потрібен мок, стоїть директива `//go:generate mockery …`.

Вузькі інтерфейси роблять тести коротшими: мок має два методи замість шести.

## 6. Контекст і час очікування

- `context.Context` — завжди перший параметр. **[авто]** `revive`, `noctx`.
- Час очікування задає транспорт: кожен обробник обгортає контекст у `context.WithTimeout`, а значення лежать у константах `timeout<Дія>` на початку файлу.
- Кожен виклик назовні (база, GitHub, SMTP, брокер, gRPC) обмежений у часі. Виклику без обмеження бути не може.
- Фонові цикли завершуються за `ctx.Done()`. Процес зупиняється через `signal.NotifyContext`.

## 7. Помилки

1. Доменні помилки — це змінні `Err…` у `internal/domain/model/errors.go`.
2. Кожен метод починається з `const op = "<Тип>.<Метод>"`, і помилка обгортається з назвою кроку:

   ```go
   return fmt.Errorf("%s: get user: %w", op, err)
   ```

3. Помилки порівнюються через `errors.Is` / `errors.As`, ніколи через `==` чи текст.
4. Репозиторій перекладає помилки сховища на доменні: `pgx.ErrNoRows` стає `model.ErrInvalidToken`. Вище репозиторію про pgx не знає ніхто.
5. Транспорт перекладає доменні помилки на коди відповіді. Невідома помилка — це `500` із загальним текстом; внутрішні подробиці назовні не віддаються.
6. Текст помилки — малими літерами, без крапки наприкінці. **[авто]** `revive`.
7. Помилки сторонніх пакетів обгортаються, а не повертаються як є. **[авто]** `wrapcheck`.
8. Ігнорувати помилку не можна, зокрема через `_` та неперевірене приведення типу. **[авто]** `errcheck`.

## 8. Логи

- Лише `log/slog` у форматі JSON. `fmt.Println` і пакет `log` не використовуються.
- Логер береться з контексту: `ctxlog.FromCtx(ctx)`. Глобальний `slog.Default()` допустимий лише у фонових компонентах без контексту запиту.
- Викликаються варіанти з контекстом: `log.InfoContext(ctx, …)`.
- Обов'язкові поля: `component` (назва типу), `op` (назва методу), `request_id`.
- `request_id` проходить через усю систему: HTTP-заголовок → gRPC-метадані → поле `RequestID` у повідомленні черги.

| Рівень | Коли |
|---|---|
| `Debug` | вхід у метод (`"called"`), проміжні кроки |
| `Info` | завершення операції, зміна стану |
| `Warn` | помилка на боці клієнта: невалідний запит, недійсний токен |
| `Error` | операція не виконана з причини на нашому боці або в залежності |

Два правила, яких попередня версія не дотримувалася до кінця:

- **Помилку логує один шар — той, що її обробляє.** Проміжні шари лише обгортають і повертають. Інакше одна помилка дає три записи, і в логах не видно, скільки збоїв було насправді.
- **Токени, паролі та вміст листів у логи не потрапляють.** Токен підтвердження діє як пароль до підписки.

## 9. Транзакції та outbox

- Сценарій не працює з транзакцією напряму. Він викликає `transactor.WithinTransaction(ctx, func(txCtx) error)` і передає `txCtx` у репозиторії.
- Якщо зміна даних має породити повідомлення, запис у `outbox_messages` робиться в тій самій транзакції. Публікувати в брокер зі сценарію заборонено.
- Усередині транзакції немає викликів назовні (HTTP, gRPC, SMTP): вони тримають з'єднання з базою відкритим невизначений час.

## 10. Повідомлення між сервісами

- Усі контракти лежать у `shared/contracts`. Структура повідомлення поза цим пакетом не оголошується.
- Назва черги — константа `Queue<Назва>`, значення малими літерами через крапку: `subscription.activated`.
- Команда (прохання щось зробити) називається `<Дія><Об'єкт>Command`, подія (факт, що стався) — `<Об'єкт><Що сталося>Event`.
- Кожне повідомлення має поле `RequestID`.
- Черги стійкі, повідомлення зберігаються на диск, підтвердження ручне, видавець чекає підтвердження від брокера.

Поведінка споживача:

| Ситуація | Дія |
|---|---|
| Оброблено успішно | `Ack` |
| Повідомлення не розбирається | `Nack` без повторної доставки — повтор нічого не змінить |
| Тимчасовий збій залежності | `Nack` з повторною доставкою |
| Постійний збій | `Nack` без повторної доставки та запис рівня `Error` |

Доставка гарантована щонайменше один раз, тому **кожен споживач ідемпотентний**: повторне повідомлення не створює другого запису і не надсилає другого листа. Ретранслятор outbox має межу спроб; повідомлення, що її вичерпало, позначається як збійне й більше не повторюється.

## 11. HTTP API

- Усі шляхи починаються з `/api/v1`. Службові `/health`, `/version`, `/metrics` — без префікса.
- Структури запитів і відповідей лежать у `internal/transport/http/dto`. Доменна модель назовні не віддається.
- Перевірка формату вхідних даних — у транспорті, до виклику сценарію.
- Форма помилки одна на весь API:

  ```json
  { "error": "repository not found" }
  ```

  Для кількох помилок перевірки — `{ "errors": ["…", "…"] }`.

| Код | Коли |
|---|---|
| `200` | успішне читання або дія за токеном |
| `202` | підписку прийнято, лист підтвердження буде надіслано |
| `400` | тіло не розбирається або дані не пройшли перевірку |
| `404` | репозиторій не знайдено, токен недійсний |
| `409` | така підписка вже існує |
| `503` | GitHub тимчасово недоступний |
| `500` | усе інше |

## 12. База даних

- Тексти запитів — іменовані константи поруч із методом, що їх виконує. Параметри лише позиційні (`$1`, `$2`); значення в текст запиту не підставляються.
- Міграції лежать у `services/<сервіс>/migrations` і називаються `NNNNNN_<опис>.up.sql` / `.down.sql`. **Кожна `up` має `down`.**
- Міграцію, що потрапила в `main`, не редагують — додають нову.
- Таблиці та стовпці — `snake_case`, таблиці у множині. Індекс — `idx_<таблиця>_<стовпець>`.
- Час — лише `TIMESTAMPTZ`. Первинний ключ — `BIGSERIAL`.
- Сервіс читає й пише лише у власну базу.

## 13. Конфігурація

- Налаштування приходять зі змінних середовища і розбираються в структуру під час старту. Якщо обов'язкової змінної немає, сервіс не запускається.
- У коді немає адрес, портів, паролів і токенів.
- Кожна нова змінна додається в `.env.example` і в таблицю README в тому самому коміті.
- Файли `.env` до репозиторію не потрапляють: вони вказані в `.gitignore`.

## 14. Тести

- Модульний тест лежить поруч із кодом: `user_usecase.go` → `user_usecase_test.go`.
- Назва — `Test<Тип>_<Метод>`. Випадки оформлені таблицею; назва випадку починається з результату: `"success - new user created"`, `"error - repository not found"`.
- Перевірки — через `testify`: `require` там, де далі продовжувати немає сенсу, `assert` для решти. **[авто]** `testifylint`.
- Моки генерує `mockery` у `internal/mocks`. Згенеровані файли вручну не редагуються.
- Допоміжні функції тесту викликають `t.Helper()`.
- Тести запускаються з `-race`.
- Модульний тест не ходить у мережу й не потребує Docker. Усе, що потребує справжньої бази чи брокера, — це інтеграційний тест у `tests/integration` на Testcontainers.

Що обов'язково покрито модульними тестами: кожен сценарій (успішна гілка та кожна доменна помилка), перекладання помилок у репозиторії та транспорті, поведінка споживача для кожного рядка таблиці з розділу 10.
