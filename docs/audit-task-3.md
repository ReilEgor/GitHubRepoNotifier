## 1. Топ-3, де «зелені» тести не ловлять реальні баги

### 1.1. Ключ API перевіряється без тесту «майже правильного» ключа (B08)

- **Баг:** перевірка `subtle.ConstantTimeCompare(header, key) != 1` замінена на «заголовок починається з ключа». Тоді `X-API-Key: smoke-keyANYTHING` проходить автентифікацію.
- **Результат:** модульні, інтеграційні й E2E зелені.
- **Чому:** усі тести автентифікації беруть або порожній заголовок, або `wrong`/`nope`: повністю чужий рядок. Жодного випадку «правильний ключ + хвіст», «обрізаний ключ», «ключ в іншому регістрі». Така заміна виглядає як безневинний рефакторинг (`strings.HasPrefix`), а відчинає всі захищені ендпоінти.
- **Де:** `services/subscription/internal/transport/http/middleware/request.go:59`; тести — `middleware_test.go`, `handler_test.go`, `integration/journey_test.go`, `e2e/tests/errors.spec.ts`.
- **Підсилення (пропозиція, не виконано):** табличний тест `TestAPIKey` у `middleware_test.go` з рядками: ключ + суфікс, префікс ключа, ключ в іншому регістрі, ключ з пробілом, порожній, правильний. Такий тест має падати на B08 (перевірити повторним запуском скрипта).

### 1.2. Гарди «0 змінених рядків» і сам `Delete` не виконуються під час гонки (B03, B05, B06)

- **Баги:**
  - B05 — `Confirm` у репозиторії не перевіряє `RowsAffected() == 0`;
  - B06 — те саме для `Delete`;
  - B03 — сценарій `Unsubscribe` ігнорує помилку `Delete`.
- **Результат:** усі три зелені на всіх рівнях.
- **Чому:** ці перевірки існують для одного випадку: два запити з одним токеном, обидва встигли прочитати підписку, перший змінив рядок, другий отримав 0 рядків і має відповісти `404` без події в outbox ([errors.md](spec/errors.md), «Поведінка на збоях»). Інтеграційний тест `TestUnsubscribe/two parallel requests with one token give exactly one 200 and one 404` це **заявляє**, але без гарда теж проходить. Імовірно, тест запускає два запити паралельно, але нічого не змушує другий прочитати підписку до того, як перший її видалить, тож на практиці виходить послідовний сценарій, а не гонка (причину я не досліджував, є лише факт, що без гарда тест зелений). Пари `confirm` + `unsubscribe` у тестах взагалі немає. Це один прогін на баг; я не перевіряв, чи тест іноді падає.
- **Де:** `repository/postgres/subscription_repository.go:112–135`, `usecase/subscription_usecase.go` (`Unsubscribe`); тест — `integration/scenarios_test.go:267`.
- **Підсилення (пропозиція, не виконано):** у harness-і інтеграційних тестів уже є `option`, що підміняє репозиторії. Додати обгортку `SubscriptionRepository`, яка затримує `GetByToken`, доки його не викличуть обидва запити (бар'єр на `sync.WaitGroup`). Тоді обидва гарантовано пройдуть `findByToken` до `Delete`, і гард справді спрацює. Додати пару `confirm` + `unsubscribe`. Тест має падати на B03, B05, B06.

### 1.3. Межа довжини email не тестується (B16) і команда на лист без `RequestID` теж (B18)

- **B16:** з `validEmail` прибрано `if len(email) > maxEmailLen { return false }`. Зелено всюди.
  - **Чому:** це ті самі два непокриті оператори, що показав профіль покриття (`handler.go:137`, `validEmail` 75%): тести ніколи не передають адресу довшу за 254. Мутаційний звіт `gremlins` цього не показав: серед його мутаторів немає видалення блоку.
  - **Підсилення (пропозиція):** рядки таблиці `TestHandler_Subscribe`: адреса з 254 і з 255 символів; перша приймається, друга дає `400`.
- **B18:** з `SendConfirmationCommand` прибрано `RequestID`. Зелено всюди.
  - **Чому:** жоден тест не читає тіло запису в outbox. Інтеграційні тести рахують рядки (`count(*)`), але не перевіряють вміст повідомлення. Без `RequestID` розривається трасування запиту через чергу. [code-style.md](../standards/code-style.md) §10 вимагає, щоб поле було в кожному повідомленні; чи воно **заповнене**, не перевіряє ніхто.
  - **Підсилення (пропозиція):** інтеграційний тест читає `payload` із `outbox_messages` і порівнює з очікуваним JSON (email, токен, `request_id` із заголовка `X-Request-ID`).

## 2. Де зелено лише завдяки інтеграційному рівню

Баги B04, B07, B14 модульні тести **пропускають**, а інтеграційні ловлять:

| Баг | Чому модульні зелені | Хто ловить |
|---|---|---|
| B04 — токен підтвердженої підписки змінюється при повторній підписці | репозиторій у пам'яті не виконує SQL `ON CONFLICT … CASE` | `TestSubscribe/confirmed pair changes nothing` |
| B07 — список старіший першим | пам'ять сортує сама | `TestList/…newest first…` |
| B14 — паралельна реєстрація одного репозиторію падає (`DO NOTHING` не повертає рядок) | пам'ять не має унікального індексу | `TestGetOrCreateRepository/parallel requests…`, `TestRepositoryRepository_Create` |

Це підтверджує вибір з ADR-0008 (перевага інтеграційним тестам), але й показує ціну швидкого шару: його зеленість нічого не каже про SQL. Прибирати модульні тести не пропоную (рішення автора: лишити).
