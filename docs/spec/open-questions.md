# Відкриті питання

Частина специфікації; короткий огляд і критерії прийняття — у [spec.md](../../spec.md).

Питання, на які потрібна відповідь автора. Стовпець «Зараз» описує, як поводиться наявний код, якщо нічого не змінювати. Питання закривається рішенням: записом у відповідному документі специфікації або ADR, після чого рядок звідси видаляється.

Відкритих питань немає.

## Відкладено до Завдання 3

Це не питання, а запланована робота. Вона лишається в специфікації, бо буде виконана; у Завданні 2 її немає, бо вимагається лише API й база даних, а ці частини не мають спостережуваного результату через API.

| Що | Чому відкладено | Що врахувати при реалізації |
|---|---|---|
| брокер повідомлень, ретранслятор outbox | потрібні лише для доставки між сервісами | записи в `outbox_messages` створюються вже зараз і накопичуються |
| сервіс `notification`, SC-2 | без брокера нікому надсилати лист | сага лишається `STARTED`, доки не з'явиться результат листа |
| споживачі подій у `tracking` (SC-3, SC-6) | потребують брокера | відписка може обігнати активацію, бо події йдуть у різні черги; видалення репозиторію без підписників — одним оператором |
| сканер релізів, SC-4 | не має зовнішнього тригера, тож не користувацький сценарій | вставка команд в outbox має бути пакетною, інакше це запит у циклі |
| подія `TagUpdatedEvent` | потребує брокера | копія тегу в `subscription` поки оновлюється лише під час підписки |

Закриті: 1 — повторна підписка відповідає `202` й оновлює запис ([api.md](api.md)); 2 — репозиторій без релізів відхиляється з `422` ([errors.md](errors.md)); 3 — запити до GitHub повторюються до трьох разів ([errors.md](errors.md), «Повтори запитів до GitHub»); 4 — тимчасові помилки SMTP повторюються, постійні відкидаються ([errors.md](errors.md), «Помилки надсилання листів»).
