# Сценарії помилок

Частина специфікації; короткий огляд і критерії прийняття — у [spec.md](../../spec.md). Відповіді кожного шляху — у [api.md](api.md).

## Як помилка стає відповіддю

1. Репозиторій перекладає помилку бази на доменну: «рядок не знайдено» стає `ErrInvalidToken` чи `ErrUserNotFound`; решта обгортається з назвою операції.
2. Адаптер `tracking` перекладає коди gRPC на доменні помилки.
3. Сценарій повертає доменну помилку або обгорнуту.
4. Обробник HTTP не ставить код сам: він передає помилку далі.
5. **Один глобальний обробник** знаходить доменну помилку через `errors.Is` і бере код і текст з каталогу нижче. Невідома помилка — `500` із загальним текстом; подробиці лише в лозі.
6. `panic` перехоплює окремий проміжний обробник і відповідає `500`.

Помилку логує лише глобальний обробник, один раз, з `request_id`; нижчі шари лише обгортають її. Ініціатора глобальний обробник не логує: він лише в логах нижчих шарів, де його вже визначено (див. [ADR-0006](../adr/0006-dependencies-through-wire-and-request-context.md)).

## Каталог помилок

| Доменна помилка | HTTP | Текст у відповіді | Рівень логу |
|---|---|---|---|
| тіло не розбирається | `400` | `invalid request body: <причина>` | `Warn` |
| `ErrInvalidEmailFormat`, `ErrInvalidRepoFormat` | `400` | список помилок у `errors` | `Warn` |
| `ErrEmailRequired` | `400` | `email is required` | `Warn` |
| немає або невірний ключ API | `401` | `unauthorized: invalid or missing API key` | `Warn` |
| `ErrRepositoryNotFound` | `404` | `repository not found` | `Warn` |
| `ErrRepositoryHasNoReleases` | `422` | `repository has no releases` | `Warn` |
| `ErrInvalidToken`, зокрема коли `UPDATE` чи `DELETE` за токеном змінили 0 рядків | `404` | `invalid or expired token` | `Warn` |
| перевищено частоту запитів | `429` | `limit exceeded` | `Warn` |
| `ErrServiceUnavailable`: GitHub або `tracking` недоступний, ліміт GitHub, перевищено час виклику `tracking` | `503` | `GitHub API is currently unavailable, please try again later` | `Error` |
| будь-яка інша, зокрема збій бази, тайм-аут запиту до бази, відмова GitHub з будь-яким іншим `4xx` | `500` | `failed to <дія>` | `Error` |
| `panic` | `500` | `internal error` | `Error` зі стеком |

Дублікат підписки помилкою не є: `POST /subscribe` для наявної пари відповідає `202` і оновлює запис (див. [api.md](api.md)).

## Поведінка на збоях

### База даних

| Ситуація | Поведінка |
|---|---|
| база недоступна на старті | пул ініціалізується на старті й виконує `SELECT now()`; якщо запит не вдався — сервіс пише помилку в лог і завершується з ненульовим кодом. Запит до сервісу, що не стартував, неможливий |
| база недоступна посеред запиту | `500`; транзакція відкочується, частково записаних даних немає |
| запит до бази довший за час на запит | контекст скасовується, запит переривається, `500` |
| дві одночасні підписки з тією самою новою поштою | обидві знаходять або створюють того самого користувача: `INSERT … ON CONFLICT` |
| дві одночасні підписки тієї самої пари | `INSERT … ON CONFLICT (user_id, repository_id) DO UPDATE`: обидві отримують `202`. Для непідтвердженої пари в записі лишається токен тієї, що завершилася пізніше, дійсне посилання — з другого листа. Для вже підтвердженої пари токен не змінюється |
| одночасні `confirm` і `unsubscribe` з одним токеном | підписку видаляє той, хто виконав `DELETE` раніше; `UPDATE` у другому запиті змінює 0 рядків → `ErrInvalidToken` → `404`, транзакція відкочується, події активації в outbox немає |
| два одночасні `unsubscribe` з одним токеном | рівно один `DELETE` видаляє рядок і дає `200`; другий видаляє 0 рядків → `ErrInvalidToken` → `404`, події немає |

### `tracking` і GitHub

| Ситуація | Поведінка |
|---|---|
| `tracking` недоступний | gRPC повертає `Unavailable` → `503`; у `subscription_db` нічого не записано |
| GitHub не відповів за `GITHUB_HTTP_TIMEOUT` (3 с на спробу) | спроба перервана й повторюється за правилами нижче; якщо всі спроби невдалі — один збій для circuit breaker → `503` |
| GitHub повертає `5xx` | повтор за правилами нижче; якщо всі спроби невдалі — один збій для circuit breaker → `503` |
| вичерпано ліміт GitHub | ліміт — відповідь `429` або `403` із заголовком `X-RateLimit-Remaining: 0`; клієнт перетворює її на `ErrRateLimitExceeded` → gRPC `ResourceExhausted` → `503`. Будь-який інший `403` — відмова в доступі: це внутрішня помилка → `500`. Заголовок `Retry-After` не враховується |
| перевищено час виклику `tracking` | gRPC `DeadlineExceeded` → `ErrServiceUnavailable` → `503` |
| 3 збої поспіль | circuit breaker розмикається: наступні 30 с запити до GitHub не надсилаються, відповідь одразу `503`; потім до 3 пробних запитів |
| повторний запит про той самий репозиторій | відповідь із кешу Redis: існування — 1 хв, реліз — 5 хв; GitHub не викликається |
| Redis недоступний | кеш у `tracking` пропускається, запит іде напряму в GitHub. Обмежувач частоти в `subscription` працює за принципом fail-open: запит пропускається, у лог іде `Warn`. Падіння Redis не вимикає ні підтвердження, ні відписку |

### Клієнт

| Ситуація | Поведінка |
|---|---|
| клієнт розірвав з'єднання | контекст запиту скасовується, незавершена транзакція відкочується |
| повторний запит із тим самим `X-Request-ID` | обробляється як новий; ідемпотентність забезпечують правила сценаріїв, а не заголовок |

### Повтори запитів до GitHub

| Правило | Значення |
|---|---|
| Що повторюється | лише безпечні запити: `HEAD /repos/{name}` і `GET /repos/{name}/releases/latest` |
| На які відповіді | тайм-аут спроби, помилка з'єднання, `5xx` |
| Що не повторюється | `200`, `404`, будь-який `4xx` (зокрема `403` і `429`): повтор не змінить результат, а ліміт GitHub лише погіршиться |
| Кількість спроб | 3: одна початкова і два повтори |
| Затримка | експоненційна: 200 мс перед другою спробою, 400 мс перед третьою |
| Час на спробу | `GITHUB_HTTP_TIMEOUT` = 3 с |
| Межа зверху | контекст запиту: якщо він скасований чи вичерпав час, повтори припиняються одразу |
| Circuit breaker | обгортає всю серію спроб: невдала серія — один збій, а не три. Інакше одна невдала підписка одразу розімкнула б його |

Найгірший випадок однієї серії — 3 × 3 с + 0,6 с ≈ 9,6 с. `GetOrCreateRepository` робить два виклики GitHub (`HEAD` і `GET`), кожен зі своєю серією, тож найгірший випадок ≈ 19,2 с. Це вміщується в 25 с на `POST /subscribe` і лишає близько 5,8 с на записи в базу.

### Помилки надсилання листів

Стосується `notification`: листа підтвердження (SC-2) і листа про реліз (SC-4).

| Тип | Що сюди входить | Поведінка |
|---|---|---|
| тимчасова | сервер недоступний, помилка з'єднання, тайм-аут, відповідь SMTP `4xx` (`421`, `450`, `451`, `452`) | команда повертається в чергу (`Nack` з повтором) і обробляється знову |
| постійна | відповідь SMTP `5xx` (`550` — скриньки не існує, `553` — невірна адреса, `554` — відхилено) | команда відкидається (`Nack` без повтору), помилка пишеться в лог рівня `Error`. Для листа підтвердження перед цим публікується результат `success = false`, і сага компенсує підписку |
| автентифікація | `535` — сервер не прийняв облікові дані відправника | як тимчасова: проблема в налаштуваннях сервісу, а не в адресі, тож лист не втрачається, доки налаштування не виправлять |

Код відповіді береться зі структурованої помилки SMTP, а не пошуком підрядка в тексті.

Наслідок: тимчасові помилки повторюються без межі. Поки поштовий сервер недоступний, команди циркулюють у черзі; кожен лист буде надіслано, щойно сервер повернеться.
