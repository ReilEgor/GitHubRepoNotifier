# API: сценарії та очікувана поведінка

Частина специфікації; короткий огляд і критерії прийняття — у [spec.md](../../spec.md). Зміни даних кожного сценарію — у [scenarios.md](scenarios.md), SQL — у [queries.md](queries.md), повний каталог помилок — у [errors.md](errors.md).

## Загальні правила

| Правило | Значення |
|---|---|
| Префікс | `/api/v1`; службові `/health`, `/version` — без префікса |
| Формат | JSON, `Content-Type: application/json` |
| Ключ API | заголовок `X-API-Key` для `POST /subscribe` і `GET /subscriptions`; посилання з листів (`/confirm`, `/unsubscribe`) ключа не потребують — їх захищає токен. Веб-сторінка просить користувача ввести ключ у поле форми й передає його в заголовку |
| ID бізнес-процесу | заголовок `X-Request-ID`: якщо клієнт його передав, використовується його значення, інакше створюється UUID; повертається в кожній відповіді й потрапляє в кожен запис логу |
| Ініціатор | пошта з запиту для `subscribe` і `subscriptions`; власник підписки, знайденої за токеном, для `confirm` і `unsubscribe`; `system` для фонових процесів. Ініціатор потрапляє в логи нижчих шарів, щойно його визначено; глобальний обробник помилок логує лише `request_id`. Між сервісами по gRPC ініціатор не передається |
| Обмеження частоти | 10 запитів на секунду з однієї адреси (`RATE_LIMIT=10-S`); понад ліміт — `429`. Лічильник зберігається в Redis; якщо Redis недоступний, запит пропускається (fail-open), у лог іде `Warn` |
| Час на запит | 25 с на `subscribe`: найгірший випадок двох викликів GitHub з повторами ≈ 19,2 с, решта лишається на записи в базу; 3 с на решту шляхів. Понад — запит переривається |
| Помилка | `{"error": "<текст>"}`; для кількох помилок перевірки — `{"errors": ["<текст>", …]}` |
| Токен | UUID v4, видається під час підписки. Змінюється лише при повторній підписці на ще непідтверджену пару. В API не повертається, бо діє як пароль до підписки. У цьому завданні листів немає, тож токен береться з бази поза кодом сервісу (див. [data.md](data.md), «Тестові дані») |

## Правила перевірки вхідних даних

| Поле | Правило | Помилка |
|---|---|---|
| `email` | обов'язкове; розбирається як адреса RFC 5322 (`net/mail`), причому `Address` має збігатися з введеним значенням, тож форма `Ім'я <a@b.c>` відхиляється; не довша за 254 символи; пробіли на краях обрізаються | `invalid email format`, `email is required` |
| `repository` | обов'язкове; `^[A-Za-z0-9._-]{1,100}/[A-Za-z0-9._-]{1,100}$`; пробіли на краях обрізаються | `invalid repository format (expected 'owner/repo')` |
| `token` | непорожній сегмент шляху | `token is required` |

Регістр не змінюється: пошта й назва зберігаються так, як їх передав клієнт, після обрізання пробілів. Тому `User@Example.com` і `user@example.com` — різні користувачі, а `Golang/Go` і `golang/go` — різні записи репозиторію, хоча GitHub вважає їх одним.

## POST /api/v1/subscribe

Сценарій SC-1. Створює непідтверджену підписку й записує в outbox команду на лист підтвердження. Публікація команди й сам лист відкладені на Завдання 3.

Запит:

```http
POST /api/v1/subscribe
X-API-Key: <ключ>
Content-Type: application/json

{"email": "user@example.com", "repository": "golang/go"}
```

Поведінка:

1. Перевірити формат обох полів; якщо є помилки — повернути їх усі разом.
2. Викликати `tracking.GetOrCreateRepository(repository)`: `tracking` знаходить репозиторій у своїй базі або перевіряє його на GitHub і зберігає з поточним тегом.
3. Зберегти локальну копію репозиторію з тегом із відповіді.
4. В одній транзакції: знайти або створити користувача й створити підписку чи оновити наявну (`Upsert`). Якщо пара вже підтверджена, токен і `is_confirmed` не змінюються, і на цьому все: ні саги, ні команди в outbox. Інакше (нова або непідтверджена пара): новий токен, `is_confirmed = false`, сага й команда `SendConfirmationCommand` в outbox.

Успіх — `202 Accepted`:

```json
{"message": "Subscription initiated. Please check your email to confirm."}
```

| Ситуація | Код | Тіло |
|---|---|---|
| тіло не JSON або бракує поля | `400` | `{"error": "invalid request body: …"}` |
| формат пошти чи назви невірний | `400` | `{"errors": [ … ]}` |
| немає або невірний ключ API | `401` | `{"error": "unauthorized: invalid or missing API key"}` |
| репозиторію немає на GitHub | `404` | `{"error": "repository not found"}` |
| у репозиторію немає жодного релізу | `422` | `{"error": "repository has no releases"}` |
| пара вже підписана, але непідтверджена | `202` | те саме, що й для нової: новий токен, новий лист підтвердження |
| пара вже підтверджена | `202` | нічого не змінюється: токен і підтвердження ті самі, саги й команди на лист немає |
| перевищено частоту запитів | `429` | `{"error": "limit exceeded"}` |
| `tracking` або GitHub недоступний: збій, тайм-аут, вичерпано ліміт GitHub, перевищено час виклику | `503` | `{"error": "GitHub API is currently unavailable, please try again later"}` |
| збій бази чи будь-яка інша помилка | `500` | `{"error": "failed to subscribe"}` |

## GET /api/v1/confirm/{token}

Сценарій SC-3. Підтверджує підписку.

Поведінка:

1. Знайти підписку за токеном.
2. В одній транзакції: `is_confirmed = true` і запис в outbox події `SubscriptionActivatedEvent`. `UPDATE` повертає кількість змінених рядків: якщо 0 (підписку видалила одночасна відписка), повертається `ErrInvalidToken`, транзакція відкочується, події в outbox немає.

Успіх — `200 OK`:

```json
{"message": "subscription confirmed successfully"}
```

Повторне підтвердження вже підтвердженої підписки — теж `200`: стан не змінюється, подія записується в outbox ще раз, і її споживач має бути ідемпотентним.

| Ситуація | Код | Тіло |
|---|---|---|
| токен не знайдено | `404` | `{"error": "invalid or expired token"}` |
| збій бази | `500` | `{"error": "failed to confirm subscription"}` |

## GET /api/v1/subscriptions?email={email}

Сценарій SC-5. Повертає всі підписки користувача, підтверджені й ні, від найновішої.

Успіх — `200 OK`:

```json
{
  "subscriptions": [
    {
      "id": 1,
      "email": "user@example.com",
      "repository_name": "golang/go",
      "confirmed": true,
      "last_seen_tag": "go1.25.3",
      "created_at": "2026-10-24T18:00:00Z"
    }
  ],
  "total": 1
}
```

`last_seen_tag` — `null`, якщо в репозиторію ще немає релізу. Для пошти без підписок — `{"subscriptions": [], "total": 0}`.

| Ситуація | Код | Тіло |
|---|---|---|
| параметра `email` немає | `400` | `{"error": "email is required"}` |
| формат пошти невірний | `400` | `{"error": "invalid email format"}` |
| немає або невірний ключ API | `401` | `{"error": "unauthorized: invalid or missing API key"}` |
| збій бази | `500` | `{"error": "failed to list subscriptions"}` |

Відповідь будується одним запитом до бази незалежно від кількості підписок (див. [queries.md](queries.md)).

## GET /api/v1/unsubscribe/{token}

Сценарій SC-6. Видаляє підписку.

Поведінка:

1. Знайти підписку за токеном.
2. В одній транзакції: видалити підписку й записати в outbox подію `UnsubscriptionActivatedEvent`. `DELETE` повертає кількість видалених рядків: якщо 0 (токен уже використано в одночасному запиті), повертається `ErrInvalidToken`, транзакція відкочується, події в outbox немає.

Успіх — `200 OK`:

```json
{"message": "You have been successfully unsubscribed"}
```

| Ситуація | Код | Тіло |
|---|---|---|
| токен не знайдено, зокрема повторна відписка або програш у гонці з одночасною відпискою | `404` | `{"error": "invalid or expired token"}` |
| збій бази | `500` | `{"error": "failed to unsubscribe"}` |

## gRPC: TrackingService.GetOrCreateRepository

Внутрішній виклик `subscription` → `tracking`. Метадані: `x-api-key`, `x-request-id`; ініціатор не передається.

| Поле | Значення |
|---|---|
| Запит | `full_name` — `власник/назва` |
| Відповідь | `id`, `full_name`, `last_seen_tag` |

Поведінка:

1. Знайти репозиторій у `tracker_db` за назвою; якщо є — повернути.
2. Інакше перевірити на GitHub, що репозиторій існує, і запитати останній реліз. Якщо релізу немає (GitHub відповідає `404` на запит останнього релізу) — повернути `FailedPrecondition`, нічого не зберігаючи.
3. Зберегти репозиторій із тегом і повернути.

| Ситуація | Код gRPC | Що отримує `subscription` |
|---|---|---|
| немає або невірний ключ | `Unauthenticated` | внутрішня помилка → `500` |
| порожня або невалідна назва | `InvalidArgument` | внутрішня помилка → `500` |
| репозиторію немає на GitHub | `NotFound` | `ErrRepositoryNotFound` → `404` |
| у репозиторію немає жодного релізу | `FailedPrecondition` | `ErrRepositoryHasNoReleases` → `422` |
| GitHub недоступний, розімкнений circuit breaker | `Unavailable` | `ErrServiceUnavailable` → `503` |
| ліміт GitHub: відповідь `429` або `403` із заголовком `X-RateLimit-Remaining: 0` | `ResourceExhausted` | `ErrServiceUnavailable` → `503` |
| перевищено час виклику | `DeadlineExceeded` | `ErrServiceUnavailable` → `503` |
| інша помилка | `Internal` | внутрішня помилка → `500` |

### Статичний режим `tracking`

На першому етапі `tracking` відповідає з фіксованого списку замість бази й GitHub, але gRPC-контракт, сервер і адаптер у `subscription` ті самі, що й далі. При заміні статики на базу змінюється лише збирання залежностей. Негативні гілки задаються іменами, що проходять перевірку формату `власник/назва`:

| Назва репозиторію | Відповідь `tracking` |
|---|---|
| `static/existing` | `id`, `full_name`, `last_seen_tag = v1.0.0` |
| `static/not-found` | `NotFound` |
| `static/no-releases` | `FailedPrecondition` |
| `static/unavailable` | `Unavailable` |

Точні імена уточнюються в плані реалізації.
