# ADR-0005: PostgreSQL, драйвер pgx і SQL без ORM

- **Статус:** accepted
- **Дата:** 2026-10-24
- **Автор:** Єгор Рейль

## Контекст і проблема

Сервіси `subscription` і `tracking` мають власні бази ([ADR-0001](0001-split-into-three-services.md)). Дані реляційні: користувачі, репозиторії, підписки зі зв'язками й унікальними парами ([data.md](../spec/data.md)). Сценарії вимагають атомарно змінювати кілька таблиць і записувати повідомлення в outbox у тій самій транзакції. Запитів небагато, і кожен уже описано в [queries.md](../spec/queries.md). Треба обрати СУБД і спосіб працювати з нею з Go.

## Рушії рішення

У порядку важливості:

1. **Транзакційна цілісність.** Зміна даних і запис в outbox фіксуються разом; унікальність і каскадне видалення забезпечує сама база.
2. **Специфічні можливості SQL.** `INSERT … ON CONFLICT` для ідемпотентних операцій, `FOR UPDATE SKIP LOCKED` для ретранслятора outbox у кількох екземплярах, `JSONB` для тіла повідомлення.
3. **SQL видно в коді.** Рецензент бачить саме той запит, що виконується, і може звірити його з `queries.md` та перевірити на N+1.
4. **Тестованість.** Основна перевірка репозиторіїв і сценаріїв — інтеграційні тести на справжній базі; можливість порахувати кількість запитів у тесті.
5. **Мінімум прошарків між кодом і базою.**

## Розглянуті варіанти

СУБД:

- PostgreSQL.
- MySQL.
- MongoDB.

Доступ із Go:

- `pgx/v5` і сирий SQL.
- `sqlc`: SQL у файлах, Go-код генерується з них.
- GORM: ORM з моделями й побудовою запитів.
- `database/sql` з драйвером і `sqlx`.

## Рішення

Обрано **PostgreSQL і `pgx/v5` з пулом `pgxpool`; SQL — іменовані константи поруч із методом репозиторію**.

- Цілісність і SQL: PostgreSQL дає все з рушіїв 1 і 2 в одній СУБД — транзакції, обмеження, `ON CONFLICT`, `SKIP LOCKED`, `JSONB`. MongoDB не тримає реляційних обмежень, а MySQL не має `ON CONFLICT … RETURNING`, що ускладнює ідемпотентні вставки.
- Видимість: запит лежить текстом поруч із методом, без перекладу з моделей ORM. Що написано — те й виконується.
- Тестованість: `pgx` має інтерфейс трасування запитів — на ньому побудовано тест кількості запитів; для інтеграційних тестів — Testcontainers зі справжнім PostgreSQL. Модульні тести репозиторіїв з імітацією бази (`pgxmock`) не потрібні: SQL перевіряє сама база.
- Прошарки: `pgx` працює з протоколом PostgreSQL напряму, без `database/sql`, і повертає типізовані помилки сервера (`pgconn.PgError` з кодом), за якими репозиторій розпізнає, наприклад, порушення унікальності.

## Наслідки

- **Добре:** усі гарантії з рушіїв 1 і 2 дає база, а не код.
- **Добре:** перелік запитів у `queries.md` збігається з константами в коді один до одного.
- **Добре:** N+1 перевіряється тестом, а не на око.
- **Погано:** читання рядків у структури пишеться вручну (`Scan` по полях); помилка в порядку полів видна лише в тесті.
- **Погано:** відповідність SQL схемі не перевіряється під час компіляції, як у `sqlc`. Її ловлять інтеграційні тести, тож без них зміна схеми може зламати запит непомітно.
- **Погано:** міграції — окремий інструмент (`golang-migrate`), а не частина бібліотеки доступу.
- **Погано:** код прив'язаний до PostgreSQL: перехід на іншу СУБД означає переписати репозиторії.

## Підтвердження

- У `go.mod` сервісів немає ORM; SQL живе лише в `internal/repository/postgres`.
- Шар сценаріїв не може імпортувати `pgx`: `.go-arch-lint.yml` дозволяє сценаріям лише `uuid` і спільні `ctxlog` та `contracts`.
- Пул створюється на старті й виконує `SELECT now()`; якщо запит не вдався, сервіс не стартує.
- Тест кількості запитів: перегляд підписок — один запит незалежно від кількості підписок.
- `forbidigo` у `.golangci.yml` забороняє `fmt.Sprintf` у `internal/repository`: запит збирається лише з літерала й позиційних параметрів.

## Плюси та мінуси варіантів

### PostgreSQL

- Плюс: транзакції, обмеження, `ON CONFLICT … RETURNING`, `SKIP LOCKED`, `JSONB`.
- Мінус: ще один сервіс для запуску локально; вирішується Docker Compose.

### MySQL

- Плюс: так само реляційна й транзакційна.
- Мінус: немає `ON CONFLICT … RETURNING`; ідемпотентна вставка з поверненням `id` потребує двох запитів.
- Був би кращим, якби: інфраструктура вже стояла на MySQL.

### MongoDB

- Плюс: гнучка схема, просте горизонтальне масштабування.
- Мінус: унікальні пари й каскадне видалення доведеться підтримувати кодом; транзакції між колекціями дорожчі.
- Був би кращим, якби: дані були документами без зв'язків.

### `pgx/v5` і сирий SQL

- Плюс: повний контроль, видимий SQL, трасування, типізовані помилки.
- Мінус: ручний `Scan`, немає перевірки SQL під час компіляції.

### `sqlc`

- Плюс: SQL лишається видимим, а типобезпечний код і перевірка запитів проти схеми генеруються.
- Мінус: крок генерації в конвеєрі; динамічні запити незручні.
- Був би кращим, якби: запитів було кілька десятків і схема часто змінювалась.

### GORM

- Плюс: менше коду для простих операцій, міграції з моделей.
- Мінус: SQL прихований, легко отримати N+1 через ліниві зв'язки; `ON CONFLICT` і `SKIP LOCKED` однаково доводиться писати сирим SQL.
- Був би кращим, якби: переважали прості CRUD-операції без вимог до конкретних запитів.

### `database/sql` і `sqlx`

- Плюс: стандартний інтерфейс, автоматичне читання в структури (`sqlx`).
- Мінус: прошарок над драйвером, помилки сервера менш типізовані, немає трасування на рівні `pgx`.

## Додаткова інформація

- Схема й індекси — [data.md](../spec/data.md), запити — [queries.md](../spec/queries.md).
- **Tagged templates.** Вимога писати сирий SQL через tagged templates стосується JavaScript; у Go такого механізму немає. Суть вимоги — SQL як літерал із параметрами, а не рядок, зібраний конкатенацією. Еквівалент у Go: іменована константа з позиційними `$n`; `fmt.Sprintf` і конкатенація в запитах заборонені лінтером.
- **Розміщення моделей.** Одна стратегія: сутності — у `internal/domain/model` без тегів; DTO — у `internal/transport/http/dto`; типи protobuf — лише на межі gRPC й мапляться на сутності на межі шару. Окремих структур-рядків БД немає: репозиторій читає рядок явним `Scan` у сутність.
- Де відкривається транзакція — [ADR-0007](0007-transaction-boundary-through-transactor.md).
- Рішення варто переглянути на користь `sqlc`, якщо кількість запитів суттєво зросте.
