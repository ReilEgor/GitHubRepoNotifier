# ADR-0008: Три рівні перевірок: швидкі, інтеграційні й smoke із Docker Compose

- **Статус:** accepted
- **Дата:** 2026-10-24
- **Автор:** Єгор Рейль

## Контекст і проблема

Сервіси отримують PostgreSQL і Redis ([ADR-0005](0005-postgresql-with-pgx-and-plain-sql.md)), а тести перевіряють сценарії разом із базою. [ADR-0004](0004-checks-in-one-script-run-by-hooks-and-ci.md) тримає `pre-commit` і `pre-push` швидкими, а повільне виносить у CI, і залишає окремим рішенням, що робити зі smoke-тестом, коли з'явиться база. Є три питання: де запускати тести, що потребують Docker, як ізолювати базу між прогонами й що робити зі smoke.

## Рушії рішення

У порядку важливості:

1. **Hooks лишаються швидкими й без Docker**, інакше їх почнуть обходити.
2. **Тест не залежить від попередніх прогонів:** кожен працює на чистій базі.
3. **Те, що перевіряє тест, збігається з тим, що працює в проді:** та сама схема, ті самі міграції.
4. **Порти не конфліктують із локальними сервісами** розробника.

## Розглянуті варіанти

- Три рівні: швидкі перевірки без Docker; інтеграційні тести на Testcontainers за build tag в окремому job CI; smoke на Docker Compose лише в CI.
- Усе в `pre-push`: просто, але Docker стає обов'язковим для кожного push.
- Інтеграційні тести й smoke лише в CI; локально нічого.

## Рішення

Обрано **три рівні**.

| Ціль | Що робить | Docker | Де запускається |
|---|---|---|---|
| `make unit` | модульні тести з `-race` | ні | `pre-push`, CI |
| `make check` | формат, лінтер, межі шарів, модульні тести, збірка | ні | вручну, CI |
| `make test-integration` | інтеграційні тести на Testcontainers, build tag `integration` | так | окремий job CI, вручну |
| `make test` | `unit` + `test-integration` | так | вручну |
| `make smoke` | Docker Compose: PostgreSQL, Redis, міграції, сервіси; проходить підписку → підтвердження → перегляд → відписку | так | лише CI |

Деталі, що входять у рішення:

- **Ізоляція бази.** Один контейнер Testcontainers на пакет тестів; у ньому `CREATE DATABASE` з унікальною назвою на кожен тест.
- **Міграції в тестах.** Схему застосовує бібліотека `golang-migrate` з коду, ті самі файли, що й у Compose (там їх запускає контейнер `migrate/migrate`). Окремий тест `up` → `down` → `up` на порожній базі перевіряє, що кожна міграція зворотна.
- **Порти Compose:** `15432` (`subscription_db`), `15433` (`tracker_db`), `16379` (Redis). Стандартні 5432–5434 і 6379 не використовуються.
- **Тестові дані.** Сід з відомими токенами лежить у `services/<сервіс>/migrations/testdata/` і застосовується лише тестовим харнесом ([data.md](../spec/data.md)).
- **Перевага типів тестів.** Інтеграційні тести на справжній базі — основний спосіб перевірки сценаріїв і репозиторіїв; модульні покривають лише те, що через базу перевірити не можна.

Як це відповідає рушіям:

- Швидкі hooks: `pre-commit` лишається як є, `pre-push` запускає `make unit` і збірку; нічого з Docker.
- Чисті прогони: окрема база на тест, без залежності від порядку тестів.
- Збіг із продом: схема з тих самих файлів міграцій.
- Порти: нестандартні, у діапазонах, які не використовують типові локальні сервіси.

## Наслідки

- **Добре:** `git push` не вимагає Docker, а інтеграційні й smoke-перевірки не зникають, а виконуються в CI.
- **Добре:** кожен інтеграційний тест ізольований, їх можна запускати паралельно й у довільному порядку.
- **Добре:** міграції перевіряються автоматично, зокрема зворотний бік `down`.
- **Погано:** помилку, яку ловлять лише інтеграційні тести чи smoke, розробник бачить після push, а не перед ним. Локально їх можна запустити вручну.
- **Погано:** `make smoke` перестає бути швидкою перевіркою, що сервіс стартує: пул бази ініціалізується на старті й падає без бази, тож поточний smoke без Docker більше не працює й переходить у CI.
- **Погано:** інтеграційні тести повільніші за модульні; контейнер на пакет скорочує, але не усуває цю ціну.
- **Погано:** для `make test-integration` потрібен Docker локально, а на Windows — запущений Docker Desktop.

## Підтвердження

- `scripts/check.sh` має цілі `unit`, `integration`, `smoke`; `.githooks/pre-push` викликає лише `unit` і збірку.
- CI має окремі job: лінтер, модульні тести, інтеграційні тести, smoke із Compose.
- Інтеграційні тести мають `//go:build integration` і не запускаються командою `go test ./...` без тегу.
- Тест `up` → `down` → `up` проходить на порожній базі.

## Плюси та мінуси варіантів

### Три рівні

- Плюс: швидкі hooks, повільне в CI, нічого не вимкнено.
- Мінус: частину помилок видно лише після push.

### Усе в `pre-push`

- Плюс: усе перевіряється до відправлення.
- Мінус: Docker обов'язковий для кожного push, а `pre-push` триває хвилини.
- Був би кращим, якби: інтеграційних тестів було мало й вони виконувалися за секунди.

### Лише CI

- Плюс: нічого не налаштовувати локально.
- Мінус: інтеграційні тести неможливо запустити перед відправленням; зворотний зв'язок повільний.
- Був би кращим, якби: Docker не був доступний на машині розробника.

## Додаткова інформація

- Docker Compose для smoke-тесту з'являється разом із кодом бази.
