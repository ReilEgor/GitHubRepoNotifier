# ADR-0004: Перевірки живуть в одному скрипті, який запускають hooks і CI

- **Статус:** accepted
- **Дата:** 2026-10-14
- **Автор:** Єгор Рейль

## Контекст і проблема

Код має проходити формат, лінтер, перевірку меж шарів, тести, збірку й smoke-тест. У попередній версії лінтер запускався лише в CI, і в історії лишилися коміти на кшталт `fix: linter`: помилку стилю помічали вже після відправлення. Треба вирішити, які перевірки обов'язкові, коли вони запускаються і чим.

## Рушії рішення

У порядку важливості:

1. **Локальний результат збігається з результатом CI.** Одна й та сама команда в обох місцях.
2. **Брудний код зупиняється якнайраніше**, до появи коміту.
3. **Коміт не має тривати довго**, інакше hooks почнуть обходити.
4. **Без додаткового середовища виконання.** Для роботи з репозиторієм досить Go і Git, зокрема на Windows.

## Розглянуті варіанти

- Перевірки лише в CI.
- Менеджер hooks: `lefthook` або `pre-commit`.
- Власний скрипт `scripts/check.sh`, який викликають hooks із `.githooks/`, `Makefile` і CI.

## Рішення

Обрано **власний скрипт**, тому що він задовольняє всі чотири рушії.

- Одна команда: hooks і `make` викликають `scripts/check.sh <перевірка>`, CI викликає `make`; розійтися їм нема де.
- Якнайраніше: `pre-commit` запускає формат, лінтер і межі шарів.
- Швидкість: повільні перевірки — тести, збірка, smoke — винесено в `pre-push`.
- Середовище: скрипт написано на `sh`, який постачається з Git, зокрема з Git for Windows. `pre-commit` потребував би Python, `lefthook` — окремого бінарного файла.

Набір перевірок і їхній розподіл:

| Перевірка | commit | push | CI |
|---|:-:|:-:|:-:|
| формат | ✔ | | ✔ |
| лінтер і статичний аналіз | ✔ | | ✔ |
| межі шарів | ✔ | | ✔ |
| модульні тести з детектором гонок | | ✔ | ✔ |
| збірка | | ✔ | ✔ |
| smoke-тест | | ✔ | ✔ |

## Наслідки

- **Добре:** помилка формату чи лінтера не потрапляє в історію.
- **Добре:** перевірку можна запустити вручну тією самою командою, якою її запускає hook.
- **Добре:** hooks лежать у репозиторії й проходять рецензію як код.
- **Погано:** hooks треба ввімкнути один раз після клонування (`make setup`); без цього вони не діють.
- **Погано:** hook можна обійти через `--no-verify`. Тому CI повторює всі перевірки, а не довіряє локальним.
- **Погано:** `pre-commit` перевіряє всю робочу теку, а не лише файли з коміту: незакінчена правка в сусідньому файлі блокує коміт.
- **Погано:** менеджер hooks уміє запускати перевірки паралельно й лише для змінених файлів; у власному скрипті цього немає.
- **Погано:** лінтер у CI запускає офіційна дія GitHub, а не скрипт; збіг гарантує лише однакова версія та спільний `.golangci.yml`.

## Підтвердження

- `.githooks/pre-commit` і `.githooks/pre-push` містять лише виклики `scripts/check.sh`.
- Кожна ціль перевірки в `Makefile` викликає той самий скрипт; `.github/workflows/ci.yml` запускає `make test` і `make smoke`.
- Сім спроб із результатами — у `standards/checks.md`, розділ «Доказ, що конвеєр блокує».

## Плюси та мінуси варіантів

### Лише CI

- Плюс: нічого не треба налаштовувати локально.
- Мінус: помилку видно через кілька хвилин після відправлення, і її виправлення стає окремим комітом.
- Був би кращим, якби: перевірки тривали довго або потребували середовища, якого немає локально.

### Менеджер hooks

- Плюс: паралельний запуск, фільтр за зміненими файлами, декларативна конфігурація.
- Мінус: ще одна залежність, яку має встановити кожен, хто клонує репозиторій; CI однаково потребував би окремого опису тих самих команд.
- Був би кращим, якби: над проєктом працювала команда, а перевірок було так багато, що без паралельного запуску коміт тривав би хвилини.

### Власний скрипт

- Плюс: одна точка входу, жодних додаткових залежностей.
- Мінус: послідовний запуск, перевірка всієї теки, ручне ввімкнення.

## Додаткова інформація

- Версії інструментів зафіксовано в `Makefile` і в CI.
- Зараз smoke-тест запускає бінарні файли напряму. Коли сервісам знадобляться база й брокер, він підніматиме їх через Docker Compose і, ймовірно, перейде з `pre-push` у CI — це буде окреме рішення.
