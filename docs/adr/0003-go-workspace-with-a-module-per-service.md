# ADR-0003: Go, один репозиторій, окремий модуль на сервіс

- **Статус:** accepted
- **Дата:** 2026-10-14
- **Автор:** Єгор Рейль

## Контекст і проблема

Система складається з трьох сервісів і спільного коду ([ADR-0001](0001-split-into-three-services.md)). Треба обрати мову й спосіб розкласти код: скільки репозиторіїв і скільки модулів.

## Рушії рішення

У порядку важливості:

1. **Межі між сервісами перевіряє інструмент**, а не рецензент.
2. **Одна зміна контракту — один pull request.** Видавець і споживач повідомлення мають змінюватися разом.
3. **Досвід автора.** Проєкт веде одна людина, основна мова якої — Go; попередня версія системи теж написана на Go.
4. **Мінімум інфраструктури для запуску перевірок.**

## Розглянуті варіанти

- Go, один репозиторій, один модуль із пакетами сервісів.
- Go, один репозиторій, модуль на сервіс і спільний модуль, об'єднані `go.work`.
- Go, окремий репозиторій на сервіс.

Інші мови не розглядалися через третій рушій: зміна мови означала б відмовитися від наявного досвіду без вигоди для вимог системи.

## Рішення

Обрано **один репозиторій із модулем на сервіс**, тому що лише він задовольняє перші два рушії одночасно.

- Межі: пакети сервісу лежать у його `internal`, тому імпорт з іншого модуля не компілюється. В одному модулі `internal` спільний для всіх, і сервіси можуть імпортувати один одного.
- Контракти: `shared/contracts` змінюється тим самим комітом, що й обидва сервіси, які ним користуються. З окремими репозиторіями це три pull request і версіонування спільного модуля.
- Досвід та інфраструктура: потрібен лише компілятор Go; `go.work` об'єднує модулі локально без публікації версій.

## Наслідки

- **Добре:** сервіс не може імпортувати внутрішній код іншого — це помилка компіляції.
- **Добре:** у кожного сервісу власний перелік залежностей у `go.mod`.
- **Добре:** зміна контракту атомарна.
- **Погано:** команди Go не працюють із шаблоном на весь репозиторій (`./...` з кореня). Лінтер, перевірка шарів і тести запускаються окремо в кожному модулі; це ховає `scripts/check.sh`.
- **Погано:** кожен сервіс має рядок `replace` на `../../shared`, тож модуль не можна підключити поза цим репозиторієм.
- **Погано:** `shared` стає місцем, куди зручно скласти все спільне. Специфікація обмежує його вміст, але це правило тримається на рецензії.

## Підтвердження

- `go.work` перелічує чотири модулі: `shared`, `services/subscription`, `services/tracking`, `services/notification`.
- Увесь код сервісу, крім `cmd`, лежить у `internal`.
- `make lint`, `make arch` і `make test` проходять по кожному модулю окремо.

## Плюси та мінуси варіантів

### Один модуль

- Плюс: найпростіше: один `go.mod`, команди працюють з кореня.
- Мінус: `internal` спільний, тож межу між сервісами довелося б описувати правилами лінтера й стежити, щоб їх не обійшли.
- Мінус: залежності всіх сервісів змішані в одному `go.mod`.
- Був би кращим, якби: сервіси були модулями одного процесу, а не окремими одиницями розгортання.

### Модуль на сервіс в одному репозиторії

- Плюс: межі на рівні компілятора, атомарні зміни контрактів.
- Мінус: перевірки по модулях, `replace`, ризик розростання `shared`.

### Репозиторій на сервіс

- Плюс: повна незалежність історії, прав доступу й випусків.
- Мінус: зміна контракту розтягується на кілька pull request; спільний модуль треба версіонувати й публікувати.
- Був би кращим, якби: сервіси вели різні команди з різним графіком випусків.

## Додаткова інформація

- Версію Go зафіксовано в `go.mod` кожного модуля, у `go.work` і в CI; вона має збігатися.
- Бібліотеки (HTTP-фреймворк, драйвер бази, клієнт брокера) обираються окремими ADR, коли з'являється код, що їх потребує.
