# ADR-0009: Тести перевіряють поведінку; якість тестів міряють покриттям і мутаціями; E2E на Playwright

- **Статус:** accepted
- **Дата:** 2026-11-15
- **Автор:** Єгор Рейль

## Контекст і проблема

[ADR-0008](0008-environment-and-integration-tests.md) ввів три рівні перевірок: швидкі, інтеграційні й smoke. Бракує трьох речей: способу бачити, що саме тести покривають; способу перевірити, що «зелені» тести справді ловлять помилки; і E2E, який перевіряє систему через публічне API з асертами, а не `curl` у shell. Є також питання, куди вкладати зусилля: у модульні тести чи в інтеграційні.

## Рушії рішення

1. **Тест описує поведінку, яку бачить користувач або сусідній сервіс**, а не будову коду: рефакторинг не ламає тестів.
2. **Покриття — підказка під час написання, а не мета.** Якість тесту міряє те, чи ловить він зміну коду.
3. **Усе запускається однією командою через `scripts/check.sh`**, як у [ADR-0004](0004-checks-in-one-script-run-by-hooks-and-ci.md).
4. **Hooks лишаються швидкими й без Docker.**

## Розглянуті варіанти

- Покриття: `go test -cover` на пакет; або один профіль на модуль із `-coverpkg=./...`.
- Мутації: `gremlins`; `go-mutesting`; `ooze`.
- E2E: shell із `curl` (як зараз у smoke); Go-тест із Compose; Playwright (режим API).

## Рішення

- **Основний упор на інтеграційні тести** на справжніх PostgreSQL і Redis (Testcontainers) і на E2E. Модульні тести лишаються для чистої логіки й порогових випадків (`ratelimit`, перекладання помилок).
- **Покриття:** `make cover` (модульні + інтеграційні, потрібен Docker) і `make cover-unit`. Рахується один профіль на модуль із `-coverpkg=./...`, тож пакет вважається покритим, якщо його виконує будь-який тест. Звіт — відсоток операторів на пакет і на модуль; `COVER_MIN=<n>` валить прогін нижче порога. Генерований код, `cmd/` і допоміжні пакети тестів не рахуються.
- **Мутації:** `gremlins` `v0.6.0`, `make mutation`, лише на модульних тестах критичних пакетів. Окрім типових мутаторів увімкнено `invert-logical`, `invert-loopctrl`, `invert-assignments`: типові майже не чіпають логіку Go-сервісу. Звіти — у `reports/mutation/` (JSON).
- **E2E:** Playwright у режимі API (`e2e/`, `make e2e`). Скрипт піднімає ту саму систему, що й smoke (`stack_up`), плюс фейковий GitHub (`e2e/fake-github.mjs`), який рахує звернення; тести читають токени й стан із баз.

## Наслідки

- **Добре:** є число покриття під час роботи й окремий сигнал про якість тестів.
- **Добре:** E2E перевіряє відповіді, стан баз і кількість звернень до GitHub, чого smoke не вміє.
- **Погано:** з'являється Node.js як інструмент розробки (`e2e/package.json`, версії зафіксовано) і `gremlins` у `make setup`.
- **Погано:** `gremlins` повільний і на Windows потребує одного воркера та довгого таймауту; мутаційний прогін не входить у hooks.
- **Погано:** мутації не бачать інтеграційних тестів: `gremlins -i` запускає весь набір на кожен мутант, а з Docker це години.
- **Погано:** у системі поки немає веб-сторінки, тому Playwright працює як HTTP-клієнт і браузер не використовує.

## Підтвердження

- `make cover-unit`, `make cover`, `make mutation`, `make e2e` проходять на чистому клоні.
- CI має окремі job `e2e`, `coverage`, `mutation`.

## Плюси та мінуси варіантів

### `gremlins`

- Плюс: працює з Go-модулями, зрозумілі статуси, JSON-звіт.
- Мінус: лише п'ять типів мутаторів; падає на шаблоні `./pkg/...` у версії 0.6.0 (тому цілі в `MUTATION_TARGETS` — окремі пакети).

### `go-mutesting` / `ooze`

- Плюс: більше мутацій (`go-mutesting`), мутації як частина `go test` (`ooze`).
- Мінус: гірше з модулями й workspace; `go-mutesting` давно не оновлюється.

### Playwright

- Плюс: один інструмент для API сьогодні й для браузера, коли з'явиться сторінка; HTML-звіт.
- Мінус: залежність Node.js заради HTTP-викликів, поки сторінки немає.
- Був би кращим, якби: у системі не планувалася веб-сторінка (тоді вистачило б Go-тесту).
